# compleo

A Go tool for zsh scripts. One spec file is the single source of truth for three things:

1. **Parsing** the script's command line
2. **Usage / help message**
3. **zsh completion**

The script calls compleo near the top; compleo parses `"$@"` and prints zsh code that the script `eval`s to set variables. Completion is generated from the same spec, so the three never drift apart.

## Status

Early design phase, but the core pipeline is implemented: `go.mod` at `github.com/nesneros/compleo`, `cmd/compleo/`, `internal/spec`, `internal/parse`, `internal/shells/zsh`, `internal/generate`, `internal/cmdutil`, mise tooling, GoReleaser + GitHub Actions CI. Spec parsing, cobra/usage building, command-line parsing, zsh emission, and completion generation (both compleo's own and a wrapped script's) all work end to end — see `examples/greet`, `examples/extensions` (every compleo-added `positionals:`/`type:` combination), and `examples/macros`. Treat anything under "Open questions" as undecided and ask before choosing.

## Design decisions

- **Language:** Go.
- **Target shells:** zsh (implemented) and bash (in progress — see "Multi-shell support" below). Each supported shell gets its own `Emitter` implementation emitting that shell's syntax directly; no shared POSIX-generic compatibility layer.
- **Completion:** built on carapace, for its rich completion actions (hosts, ssh keys, brew formulae, files, ...). Spec fields for completion stay as close as possible to the carapace-spec format.
- **Macro names:** use the same names as carapace-spec/carapace-bin (e.g. `$files`, `$carapace.tools...`) — don't duplicate that naming knowledge.
- **A flag's/positional's own `completion:` lives right on its own `flags:`/`positionals:` entry**, not in a separate top-level section: plain carapace-spec keys a command's completion actions by flag name/positional index in a command-level `completion: {flag: {...}, positional: [...]}` map, because carapace retrofits completion onto a command *that already exists* — a CLI built with its own `pflag.FlagSet`, which has no completion field at all (pflag predates carapace), so completion can only be bolted on afterward as a separate, name-keyed registration (mirroring cobra's own `RegisterFlagCompletionFunc`). compleo builds the cobra tree itself from its own `Flag`/`Positional` structs, so there's no reason to keep that split: `Flag.Completion`/`Positional.Completion` (`internal/spec/flag.go`/`command.go`) hold the action-expression value directly on the entry it completes, and `Command.toCarapace()`'s `flagCompletions`/`positionalCompletions` gather them back into carapace-spec's name-keyed/index-keyed shape right before handing off to `ToCobraE()`.
  - **`spec.Command` has no `Completion` field at all** — plain carapace-spec's other top-level completion slots (`positionalany`/`dash`/`dashany`) aren't exposed to a compleo spec author, deliberately: every case we could construct for wanting one is either already better served by a variadic `positionals:` entry's own `completion:` (which auto-promotes, see below), or describes a position `internal/parse` would reject as an arity error anyway, or (for `dash`/`dashany` specifically) would promise completion behavior parsing doesn't honor, since `internal/parse` never distinguishes an argument before vs. after a literal `--`. A spec declaring `completion:` at the command level now hard-errors under `KnownFields(true)`.
  - See `positionalCompletions` in `internal/spec/command.go` for the behaviors specific to positional completion (trimming trailing undeclared entries so they don't shadow `completion.positionalany`; a trailing variadic positional's own completion also fed back as that fallback — the only way left to influence `completion.positionalany`).
  - If `completion.positionalany` would otherwise be left unset (no variadic fallback), `toCarapace()` defaults it to `$compleo.none` (`internal/spec/macros.go`) instead — an explicit zero-candidate action. Leaving it unset routes through carapace's own cobra-compat bridge for an undeclared position, whose behavior there is a trap, not a documented contract (observed to offer the cwd's files); a command the spec never gave a completion for should complete to nothing, not to that.
- **`spec.Command` duplicates carapace-spec's `command.Command`, rather than embedding/wrapping it**: `internal/spec/command.go` declares `Command` as its own independent struct — same field names/YAML tags as `command.Command`, but not the same Go type — and `internal/spec/flag.go` likewise declares compleo's own `Flag`/`FlagSet`. `toCarapace()` converts compleo's `Command`/`FlagSet`/`Flag` into carapace's own equivalents at the one point that still needs them: handing off to carapace-spec's `ToCobraE()`. The reason to duplicate rather than embed: embedding only lets compleo *add* fields the carapace type doesn't have — it can't add a field onto a carapace-owned struct like `Flag` itself. `Flag.Type`, `Flag.Completion`/`Positional.Completion`, and any future per-flag/positional validation attribute all rely on this. `Positional` has no carapace-spec equivalent to reuse in the first place.
  - Duplicating `Flag`/`FlagSet` means `FlagSet.UnmarshalYAML` (`internal/spec/flag.go`) also duplicates carapace's own flag-key parsing (`-c, --count=*!` shorthand-and-modifier syntax), plus recognizes `type:`/`completion:` as extra object-form keys. Plain carapace-spec/carapace-bin's own `FlagSet` decoder tolerates both fine (it silently ignores any object-form key besides `description`/`nargs`/`default`), so a file with these still decodes there — it just gets no typed validation or completion from them.
  - A plain `Commands []Command` field decodes recursively on its own, so `decodeYAML`'s `decoder.KnownFields(true)` strict-decoding reaches every level of the document, root included.
- **`Type` is an interface, one concrete struct per kind** (`internal/spec/type.go`): `StringType{}`/`IntType{Min, Max *int}`/`FloatType{Min, Max *float64}`/`BoolType{}`/`DurationType{}`/`PathType{}`/`EnumType{Values []string}`, each implementing `Validate(s string) error` and an unexported `hint() string` (what `--help`'s backtick-quoted type hint shows). A sum type rather than a flat struct, since `Min`/`Max`/`Values` only mean something for one or two kinds each. `Flag.Validate`/`Positional.Validate` are thin wrappers with a nil-`Type` guard — a zero-value `Flag{}`/`Positional{}` (e.g. a map lookup miss, or test code not going through YAML decode) has a nil interface, and calling a method on one panics.
  - YAML: a bare string (`type: int`) is shorthand for the object form with nothing but that kind (`type: {kind: int}`) — decoded by `decodeType` in `type.go`, called from both `FlagSet.UnmarshalYAML` and `Positional.UnmarshalYAML`. `min`/`max`/`values` nest inside `type: {...}`, never alongside a flag's own `description`/`nargs`/`default`.
  - `flagCompletions`/`positionalCompletions` (`internal/spec/command.go`) auto-fill an `EnumType` flag's or positional's own `Completion` from its own `Values` when it has none of its own — an explicitly declared `Completion` always wins over the derived one. `IntType`/`FloatType`'s `Min`/`Max` get no such derivation: the closest macro, carapace-bin's `$carapace.number.Range(start,end)`, needs the separately-installed `carapace` binary, so deriving from it would make a bounded flag's *completion* depend on something its *validation* doesn't need; declare `completion:` yourself if you want it.
- **Result delivery:** the Go program prints a zsh script; the calling script `eval`s it. Parsed values go into an associative array.
- **Architecture:** spec is built into an in-memory `cobra.Command` at runtime via `spec.Command`'s private `toCarapace().ToCobraE()`. Not carapace's `--codegen`: that writes static per-command `.go` stubs for an offline compile step, which doesn't fit "one generic binary, arbitrary spec read fresh every invocation."
- **Parsing engine:** cobra/pflag via `ToCobraE()`, not a custom parser. Cobra/pflag only register real flags for `string`/`[]string`/`bool`/`count`; other declared `type:` values (a flag's or a positional's) are plain strings to them, so `internal/parse`'s `bindFlags`/`bindPositionals` validate those itself via `spec.Flag.Validate`/`spec.Positional.Validate` — the only place an invalid type declaration is ever caught (see `bindFlags`'s own comment in `parse.go` for which unset/no-default flags are skipped and why). A flag's effective `spec.Flag` is resolved per (sub)command in `internal/parse`'s `wireCommand`: its own `Flags`/`PersistentFlags`, merged with whatever its ancestors declared on *their* `PersistentFlags` (not their own `Flags`) — matching cobra's own behavior of merging an ancestor's persistent flags into a subcommand's `cmd.Flags()`. Positional arity/required-ness/binding is entirely `internal/parse`'s own (cobra's `Args` is always `cobra.ArbitraryArgs`). A typed flag's `--help` shows its declared type (e.g. `` (`int`) ``) appended to the description by `Flag.toCarapace()`, since pflag's `UnquoteUsage` looks for a backtick-quoted segment and uses it as the displayed type instead of `flag.Value.Type()`.
- **Spec delivery at runtime:** the target script's spec is read from compleo's stdin, not a file-path argument — lets the calling script supply it as a heredoc, inline variable, or an external file (`compleo up < "$spec_file"`, no `cat` needed). In `parse` mode, compleo's wrapped-script argv is entirely the wrapped script's own arguments. `examples/carapace_bin_macros` uses an external file next to the script (large spec); every other example inlines its spec via a heredoc.
  - `parse`/`up`/`validate` all fail fast instead of blocking when stdin isn't piped, unlike ordinary Unix tools: `main()`'s `isPiped(os.Stdin)` checks whether stdin is a pipe/redirect vs. an interactive terminal, and `run()`'s shared block right before its `switch cmdName` returns an immediate error when it isn't. None of the three have a legitimate interactive use case — blocking would only ever mean something's wrong (a forgotten heredoc, a bad invocation), and for `parse`/`up` specifically, inside a command substitution that looks like a silent hang with no prompt, not an obvious "waiting for input."
- **compleo's own CLI vs. `parse` mode:** `parse` is a real subcommand in `cmd/compleo/spec.yaml`, like `version`/`validate`/`activate` — flags: `--name`; positionals: one variadic `args`, absorbing the wrapped script's entire argv. It's dispatched through the exact same generic path as every other compleo subcommand.
  - `"--"` is optional: it's only needed to disambiguate a wrapped script's own flag from one of compleo's own `parse`-level flags (`--name`, cobra's auto `--help`) — e.g. `compleo parse -- --name` makes `--name` the wrapped script's own. With no collision, `compleo parse world` works with no `--`. This is ordinary pflag behavior (`parseArgs` stops interpreting flags at a bare `--`), not hand-rolled parsing.
  - `version`/`validate`/`activate`/`generate`/`up` are subcommands on compleo's own CLI, not root flags, so they read the same as any other spec subcommand. There's no separate `help` subcommand, only cobra's own `--help`/`-h`, available on every (sub)command.
  - `--help` is intercepted by cobra before `RunE` runs. `internal/parse`'s `helpRequested` recurses the whole command tree checking `Flags().Changed("help")` and `Parse` sets `Result.HelpRequested` from it right after `cmd.Execute()` succeeds — this can't be inferred from `Path`/`Flags` being empty, because cobra converts `flag.ErrHelp` to a `nil` error before `Execute()` returns, so success alone doesn't say whether the matched command's `RunE` actually ran.
- **Wrapped-script completion install location:** `compleo activate` prints zsh that does `fpath+=(...)` (`compleo activate --shell=bash` prints bash wiring instead; omit `--shell` and the parent process is detected) — meant to run in `.zshrc` **before** `compinit` (`compinit`'s directory scan only sees what's already on `$fpath` when it runs). The directory (`cmdutil.CompletionDir()`) is `$COMPLEO_COMPLETION_DIR` if set, else `${XDG_DATA_HOME:-~/.local/share}/compleo/completions`; creating it is a side effect of `cmdutil.WriteCompletionFile`'s own `os.MkdirAll`, run server-side as part of `activate` itself.
  - `activate` also writes compleo's own completion to `cmdutil.CompletionDir()/_compleo`, skipping the write when content is unchanged — needed because `activate` may run on every shell startup, and touching the file every time would bump the directory's mtime, which is what makes `compinit` rescan `fpath` instead of trusting its `.zcompdump` cache. Depends on `zsh.Completion`/`Emit` being deterministic for identical input (covered by `TestCompletionIsDeterministic`).
  - If `activate` runs in an already-initialized shell (`compinit` already ran once, so adding to `$fpath` alone changes nothing for *this* session), `EmitActivate` also emits a guarded `autoload`+`compdef` loop for the current session — guarded because `compdef` doesn't exist as a command until `compinit` has run once.
  - `EmitActivate` also defines a `compleo() { command compleo "$@" }` shell function — run in `.zshrc`, so it lands in the interactive shell itself, not a subprocess. The `command` is load-bearing (without it, calling `compleo` from inside the function would recurse into itself); the point of having it at all is that a shell function, unlike every other way compleo runs, can eventually also modify the calling shell's own state, which nothing else here can do.
- **Quoting and print/exit:** `posix.Emitter` is embedded in `zsh.Emitter` and `bash.Emitter`. `Quote` is the shared single-quote form (an embedded `'` is `'\''`). `StdoutFormat` and `StderrFormat` are the shell's print formats, and `Shell` is the name `Name()` returns. They are set once on `zsh.Em` and `bash.Em` in each package's `emitter.go`; `EmitHelp` and `EmitError` are implemented from the print formats. Call sites pass `Name()` where a shell name is needed, including `shells.Completion`. Round-trip tests stay in each shell package, because they have to run that shell.
- **`zsh.Emitter.EmitResult`:** a fixed associative array named `compleo` holds every scalar flag's/positional's value (`compleo[name]=value`); a repeatable flag or variadic positional gets its own real zsh array (`compleo_<name>=(...)`) instead, since assoc-array values are scalars only. Booleans are always present as `"true"`/`"false"` (not presence/absence); count flags render as a plain integer string. See `arrayVarName`'s own comment in `internal/shells/zsh/emit.go` for how a separate array's variable name is sanitized. Iteration over `result.Flags`/`result.Positionals` is sorted (`sortedKeys`) for deterministic output, which `activate`'s skip-if-unchanged write depends on.
- **`--help` in `parse` mode:** cobra's `HelpFunc` writes straight to `OutOrStdout()` — the same stream the wrapped script evals as zsh. `runEmit` buffers the wrapped `cmd`'s output (`cmd.SetOut(&helpBuf)`), and if `HelpRequested`, emits `EmitHelp` instead of `EmitResult`. `cmd.SilenceErrors`/`SilenceUsage` (set on the wrapped `cmd` too) stop cobra from also writing its own `Error:`/`Usage:` straight to the real stderr alongside compleo's own reported error.
- **Parse errors in `parse` mode are encoded into the output, not returned as a Go error:** `EmitError` formats `"name: err"` itself, prints `print -u2 -- <Quote(...)>\nexit 2`, and returns nil. Exit 2 specifically (not `main()`'s generic exit 1), so a script checking `$?` can tell the two apart. `name` is the spec's `name:` field, not the real `$0` (compleo never sees it — `examples/greet` interpolates `${0:t}` into its own `name:` for this). This means a wrapped script needs only `eval "$(compleo parse -- "$@" <<SPEC ... SPEC)"`, no separate `|| exit $?` — the one gap this doesn't cover is if compleo itself fails to even launch, where there's no output to eval at all, so an explicit exit-code check is still the only way to catch that.
- **Env var names are Go constants, not string literals:** `internal/cmdutil/env.go` defines `EnvCompletionDir`/`EnvGenerateName`/`EnvSpecFile`/`EnvDebugLog` (the `COMPLEO_*`/`_COMPLEO_*` names) — every read or write references the constant, so the Go side setting one and the Go side reading it can't drift apart from a typo. See that file's own comment for the leading-`_` naming convention.
- **`internal/spec`'s API surface:** `ParseYAML` decodes and builds the cobra tree in one call — the one entry point everything uses. `decodeYAML`/`toCarapace`/`Apply` are private. `ParseYAML(data string, name string)` takes the spec as a plain `string`, not an `io.Reader`: every real caller already has the full spec in memory before calling it. `decodeYAML` still wraps `data` in a `strings.NewReader` internally, since `yaml.Decoder.KnownFields(true)` (needed for strict unknown-field rejection) is only available via `yaml.NewDecoder(io.Reader)`, not the package-level `yaml.Unmarshal([]byte, ...)`.
- **`compleoCmd` panics rather than returning an error on an invalid embedded `spec.yaml`:** it's built in via `go:embed`, so a parse failure there is a bug, not a runtime condition — unlike `runCarapace`/`runParse`, which parse specs genuinely coming from outside and return ordinary errors.
- **YAML library pin matters:** must use `gopkg.in/yaml.v3`, not `go.yaml.in/yaml/v3` — `spec.Command`'s `Run command.Run` field reuses the pinned `carapace-sh/carapace v1.16.3`'s `command.Run`, which has a custom `UnmarshalYAML` method tied to that specific package's `*yaml.Node` type; the other library's decoder silently won't find it. Carapace migrates to `go.yaml.in/yaml/v3` after this tag — revisit this pin together.
- **Versioning:** follows carapace-bin's pattern — `version`/`commit`/`date` vars in `cmd/compleo/version.go`, populated by GoReleaser's default ldflags. `versionString()` appends `(date) [commit]` when `version` contains "SNAPSHOT", or when `version` is still `dev` and both `date`/`commit` are set.
- **Canonical carapace org & versions:** the project lives at `carapace-sh`; `rsteube/*` repos just redirect there. Pinned: `carapace-spec v1.9.0`, `carapace v1.16.3`, `cobra v1.10.2`, `pflag v1.0.10` (see next bullet — effectively replaced by the pinned fork at runtime).
- **Full flag-syntax support:** `go.mod` has `replace github.com/spf13/pflag => github.com/carapace-sh/carapace-pflag v1.3.0`. Without it, a shorthand-only flag (`-v:`, no `--verbose`), a multi-letter single-dash flag, or an `nargs`-consuming flag (`--pair=: {nargs: 2}`) all silently fail to register — not an error, just absent: gone from `--help`, and typing it gets a generic "unknown flag" as if it were never declared (carapace-spec's `addFlagTo` error is discarded by its caller; the fork-specific registration methods it calls are invoked through a reflection shim that silently no-ops when the real `*pflag.FlagSet` doesn't have them). The fork is a drop-in `replace`, same `spf13/pflag` import path, no code changes needed anywhere in compleo.
- **Generating and serving a wrapped script's own completion:** there is no separate mode env var — `_COMPLEO_GENERATE_NAME`'s mere presence (any non-empty value) is both the name and the trigger. `main()` reads it once via `os.Getenv` and threads it down as a plain `generateName string` parameter through `run`/`runParse`/`generate.Generate`; `runParse` calls `generate.Generate` when it's non-empty, `runEmit` otherwise. A wrapped script's existing, unconditional `eval "$(compleo parse -- "$@" <<SPEC ...)"` line needs no mode-aware logic of its own:
  - unset (`""`): parse `"$@"` against the piped spec, as above (`runEmit`).
  - set: build the wrapped script's completion snippet and write it, plus a companion spec file, to `cmdutil.CompletionDir()` (skip-if-unchanged), then report success as self-exiting zsh — see `generate.Generate`. Triggered by hand (`_COMPLEO_GENERATE_NAME=greet ./greet`) or via `compleo generate <script>` (`generate.GenerateFor`, a thin wrapper that resolves `script` via `exec.LookPath` — which also accepts a path, not just a bare `$PATH` name — and re-execs it with the env var set to `filepath.Base(script)`).
  - There is no bulk/automatic regeneration across every wrapped script a user has — it's always a manual, per-script step.
  - `EmitGenerated`'s message is a one-shot activation hint for the *current* shell (a new shell picks up the file for free, since `compinit` rescans `$fpath` at startup): `"To activate completion for <name> in this shell, run: autoload -Uz _<name> && compdef _<name> <name>"`. Must autoload `_<name>` (the file's own name), not `_<name>_completion` (the function it defines inside) — autoload resolves by filename.
- **Live completion: the spec is embedded in the generated file, not re-fetched by re-running the wrapped script:** carapace's own generated snippet always re-invokes `uid.Executable() + " _carapace zsh"` — literally `compleo _carapace zsh <words>`, since `uid.Executable()` returns whatever binary is actually running, not the completed command — so compleo reaches that dispatch with no spec on stdin at all.
  - `WrappedCompletion(cmd, name, specFilePath)` leaves carapace's own invocation untouched and instead injects one line right after `function _<name>_completion {`: `local -x _COMPLEO_SPEC_FILE=<Quote(specFilePath)>` — function-scoped and exported, so it reaches the `xargs`-spawned `compleo` child but never leaks outside the function.
  - The spec's content lives in a companion file, not the env var itself: an env var is subject to OS-level size limits (`ARG_MAX`) with no graceful failure if hit; a file has no such practical limit. `generate.Generate` writes the raw, already-expanded spec bytes to `<completionDir>/.<name>.spec.yaml` (skip-if-unchanged) and embeds that *path* into the generated snippet. See its own comment for why the filename is dot-prefixed.
  - On the receiving end, `run()` in `main.go` checks `_COMPLEO_SPEC_FILE` *before* building compleo's own `ownCmd` tree, as soon as it sees `args[0] == "_carapace"`: if set, it reads the file and passes its content straight to `runCarapace`, which builds a *fresh* cobra tree from it and dispatches directly into that. If unset (compleo's own completion), falls through to the existing `ownCmd`-based `_carapace` handling.
  - A spec whose own text doesn't declare `name:` gets it prepended into the companion file (`generate.Generate`), making the file a complete, standalone spec — keyed off `declaredNamePattern` (a regex on the raw spec text), not `sp.Name`, since `sp.Name` may already be non-empty via `--name` even though the raw text has no `name:` field at all (true of `examples/greet`).
  - `scriptShell:` is the wrapping script's shell, from its shebang (`shells.ShebangShell`). `compleo generate <script>` passes the resolved script path as `_COMPLEO_SCRIPT_FILE`, and `generate.Generate` prepends `scriptShell:` when the spec text doesn't already declare it. A declared value that disagrees with the shebang is an error. A hand-run `_COMPLEO_GENERATE_NAME=greet ./greet` sets no script path, so `scriptShell:` is left unset — the same open fallback as the completion-target shell for that trigger.
  - Net effect: a wrapped script doesn't need `$PATH` at all for *using* its completion (every Tab press) — only, at most, for `compleo generate` itself. `mise.toml`'s `_.path` (adding `examples/` to `$PATH`) matters only for *generating* the demo scripts' completions.
  - **`name:` in the spec is optional:** `generate.GenerateFor` passes the resolved name through as `_COMPLEO_GENERATE_NAME`. `main()` reads that into `generateName` and `generate.Generate` uses the parameter to fill in a missing `name:`. If `name:` *is* declared and disagrees with the invoked name, `generate.Generate` fails outright — generating under the wrong name would otherwise silently break Tab-completion for what's actually typed. Without a `name:` at all, `ParseYAML` sets `cmd.Use = "<script>"` when `sp.Name == ""`, so `--help` still renders a sane synopsis instead of a blank first word.
  - **`compleo parse --name`** (typically `--name "${0:t}"`) lets a spec's heredoc drop `name:` and quote its delimiter (`<<'SPEC'`, no `$`/`` ` `` escaping anywhere in the body). `spec.ParseYAML(data, name)` fills in a missing `name:` or errors on a mismatch with a declared one before building `cmd`.
  - **`compleo up`** writes the `compleo parse --name=... -- "$@"` invocation for you, so a script doesn't need to write `--name`/`--`/`"$@"` at all: `eval "$(compleo up <<SPEC ... SPEC)"` is the whole line. `run()`'s `case "up":` calls `EmitUp` with the already-read raw spec, which prints `` eval "$(compleo parse --name="${0:t}" -- "$@" <<<%s)" `` with the spec embedded via `Quote()` as a `<<<` here-string. This means the `eval` the script runs expands into a *second* `eval "$(compleo parse ...)"` — deliberate, not an oversight: `up` genuinely cannot know the calling script's own `$0`/`"$@"` itself, so the only way to fill them in is to emit code that references them directly in the *script's own* shell context.
    - `up` doesn't branch on `_COMPLEO_GENERATE_NAME` at all — it set on the wrapped script's own invocation still reaches the *inner* `compleo parse` call unchanged (plain env var inheritance across the nested `eval`/subprocess).
    - `up` has no flags of its own. `compleo parse --name="${0:t}" -- "$@"` directly is still there for anyone who needs finer control over the invocation itself.
    - An external spec file no longer needs a hardcoded `name:` either, now that `up` always supplies one: `eval "$(compleo up < "${0:A:h}/greet.spec.yaml")"` works with a nameless file.
    - **A spec needing genuinely dynamic content** has two options, chosen by how much of the spec needs it. `examples/other_spec`'s `$spec(...)` macro needs one absolute path only the running script can compute (`${0:A:h}`) — with just that one thing dynamic, it keeps the heredoc unquoted (`<<SPEC`, not `<<'SPEC'`) straight into `up`, escaping the handful of literal `\$spec` mentions. When *most* of the spec is static and only a small dynamic piece doesn't fit a quoted heredoc at all, capture the heredoc into a variable instead (`spec=$(<<'SPEC' ... SPEC)` — no `cat` needed) and splice the dynamic piece in afterward via a plain zsh substitution (e.g. `${spec//@PLACEHOLDER@/${0:A:h}}`) before piping to `up` via `<<<`.
- **`$compleo.scripts` — compleo's first custom macro:** `internal/spec/macros.go` registers it via carapace-spec's `AddMacro`/`MacroN`. Narrower than `$executables` for `compleo generate <TAB>`: only offers executables on `$PATH` that look like they wrap compleo (`IsCompleoScript` — shebang present, plus the literal word "compleo" in the first 4KB, checked natively in Go, no `file` subprocess per candidate).
  - `actionScripts()` merges that filtered `$PATH` list with carapace's own `ActionFiles()`, since `script` (`compleo generate`'s positional) can be a path too — path candidates are unfiltered, same tradeoff the `$files` macro already has.
  - `AddMacro("scripts", ...)` registers under the internal key `_.scripts`; carapace-spec's `ActionMacro` rewrites `$<running-binary-name>.foo` to `$_.foo` before lookup, so `$compleo.scripts` only dispatches when compleo is the running binary (same mechanism carapace-bin uses for `$carapace.*`). Macro registration is global, so any wrapped script's own spec can use `$compleo.scripts` too.
- **A carapace-bin macro's first path segment is the binary carapace-spec execs, not a category label:** for any `$X.Y...` that isn't `$<running-binary>.foo`, carapace-spec's `ActionMacro` execs `X` as a literal command and passes `Y` as the macro path argument. For carapace-bin's ~130 extra macros (shell/os/net/net.http/net.ssh/ps/fs/number/text/time/color/tools.\*), the real, fully-qualified name is always `carapace.<category>.<Name>` — e.g. `$carapace.shell.Aliases`, never bare `$shell.Aliases`. Getting this wrong fails near-silently (a completion *message*, not a shell error, often `exec.LookPath` hitting Go's `exec.ErrDot` safety check) and `--help` can't catch it either, since rendering a description never dispatches the macro. Verify any carapace-bin macro reference against the installed completer's own catalog before trusting it (`carapace _carapace macro <category>.<Name> ""` also exercises dispatch, not just confirms the name is known) — don't guess a plausible-sounding one.

- **Multi-shell support (`internal/shells`):** zsh lives in `internal/shells/zsh` and is the emitter that gets installed. `internal/shells/bash` is a sketch of the same interface and is not installed (more shells may follow). `shells.EvalEmitter` (code a wrapped script evals: `EmitResult`/`EmitHelp`/`EmitError`/`EmitUp`/`EmitGenerated`) and `shells.CompletionEmitter` (the interactive shell: `WrappedCompletion`/`EmitActivate`; `Completion(cmd, shell)` is shared) both include `Quote`. `shells.Emitter` embeds the two. They live in `internal/shells` itself — not in any one shell's package. The eval emitter is installed with `SetEvalEmitter` and read back with `GetEvalEmitter()` (the `Get` prefix is only there because the interface name already occupies `EvalEmitter`). `GetCompletionEmitter()` does not store one: it returns the emitter named by `EnvCompletionShell`. `zsh.Emitter` is the zsh implementation; `bash.Emitter` satisfies the same interface but is not installed. `generate` uses both at once — see the next bullets.
- **Shell selection (`--shell`):** `activate`/`generate` take an optional `--shell` flag (`zsh` or `bash`); when it's absent, compleo auto-detects from the invoking process's parent rather than guessing blind or silently defaulting to zsh. `eval "$(compleo ...)"` always runs compleo as a direct child of the invoking shell — command substitution forks the shell and execs compleo straight into that forked PID, never through some other intermediary — so the parent PID's process name is a reliable signal, not a heuristic. Looked up with gopsutil (`github.com/shirou/gopsutil/v3/process`): the current process's `Parent()`, then that process's `Name()`. That reads `/proc` on Linux and uses sysctl on macOS, with no `ps` subprocess on the hot path, then strips a leading `-` (login shells report as `-zsh`/`-bash`).
- **`generate`'s two shells can differ:** in `compleo generate <script>` → re-exec `script` with `_COMPLEO_GENERATE_NAME` set → the script's own embedded `compleo parse` call, that inner call's parent is the *script's* shell (per its shebang) — not necessarily the interactive shell the user ran `compleo generate` from in the first place. `activate` exports `cmdutil.EnvCompletionShell` into the interactive shell. The outer `compleo generate` resolves the completion-target shell from `--shell`, else that variable, else its own parent, and passes the result down via `cmdutil.EnvCompletionShell`; the inner call cannot re-derive it from its own parent, since that parent is the wrong shell for this purpose. `EmitGenerated` needs both dialects at once: its message *content* is completion-target advice (`autoload -Uz _name && compdef _name name` is zsh-specific; bash's equivalent names a different command), but the `print ...; exit 0` statement that *delivers* that message is reached via the script's own `compleo up`/`compleo parse` call and gets `eval`'d by the script's own shell — so that wrapper must be built with the script-side emitter, not the completion-side one, even though the words inside it describe the completion-side shell.
- **Detection failure must not become a plain Go error:** `eval` captures only stdout; if shell detection fails (an unsupported/undetectable shell — PID 1 in a container, `sh`/`dash`, a shell with no `Emitter`) and compleo returns an ordinary Go error, `main()` reports it to stderr and exits 1, but stdout is empty — `eval ""` then succeeds silently and the wrapped script continues as if nothing happened, with no variables ever set. That's the same class of silent gap `isPiped`'s stdin checks already guard against. Instead, an undetectable shell must still produce a POSIX-portable error payload (plain `printf` to stderr plus `exit 2`, `'\''`-style quoting, no zsh/bash-only syntax) that `eval`s correctly under sh, bash, and zsh alike.
- **`up` forwards, not re-detects:** `up`'s emitted inner `compleo parse` call carries the already-resolved `--shell=X` explicitly, rather than having that nested invocation detect the parent shell a second time.

## Open questions (do not decide silently)

- `PathType` is still attribute-free — no way to require the value already exist, or be specifically a file vs. a directory. Resolving this is now just adding fields to `PathType{}` itself (e.g. `Exists bool`, `Must string`) and a `kind: path` case in `decodeType`'s attribute reading, the same shape `IntType`/`FloatType`'s `Min`/`Max` and `EnumType`'s `Values` already use — not a new mechanism, just not written yet. A more general per-type validation story (string pattern, etc.) beyond the kinds that already exist remains open.
- **Minimum bash version:** macOS ships `/bin/bash` 3.2 (no `declare -A`), and carapace's own bash completion snippet uses `mapfile` (bash 4+). Detecting *which* shell by parent-process name doesn't tell you *which version* of it. Undecided whether compleo requires bash ≥4 — documented as such, with the emitted bash guarded by a `BASH_VERSINFO` check that fails clearly on 3.2 rather than breaking confusingly partway through — or whether it attempts broader compatibility.
- **Fallback for the manual `generate` trigger:** `_COMPLEO_GENERATE_NAME=greet ./greet`, run by hand with no outer `compleo generate` process, has nothing to resolve and pass down the completion-target-shell env var described under "Multi-shell support" above. Undecided what it falls back to — its own parent process, always zsh, or requiring `--shell` through some other channel for this path specifically.

## Things to verify before relying on them

- That current carapace-bin still generates `pkg/actions/actions_generated.go` the way v1.0.2 does.
- A flag's/positional's own `type:`/`completion:`: plain carapace-spec/carapace-bin's `FlagSet` decoder silently ignores both (so a file with them still decodes and parses/describes correctly for a plain consumer), but that consumer gets no completion at all from `completion:` — not just an ignored key, a feature that's simply absent for them. Still open in general: whether some other future compleo-only key, nested somewhere plain carapace-spec otherwise recognizes, would also be silently tolerated — matters only if the same enriched spec file is ever meant to also be consumable directly by plain carapace-bin/carapace-spec.
- Importing `pkg/actions` links every action package; check the resulting binary size.

## Tooling: mise, not make

Use **mise** for tool versions and tasks. Do not add a Makefile.

- Tool versions (Go, golangci-lint, goreleaser, act) are pinned in `mise.toml` under `[tools]`.
- Simple tasks live in `mise.toml` under `[tasks.*]`; longer scripts are file tasks under `mise-tasks/` (e.g. `mise-tasks/ci-local`) with a `#MISE description=...` header — both run with `mise run <task>`.
- Tasks: `build`, `test`, `lint`, `fmt`, `check` (fmt check, vet, lint, test), `install`, `release-check` (`goreleaser check`, no build), `release-dry-run` (local snapshot build, no publish), `ci-local` (runs `ci.yml` locally via `act`, Docker required).
- If a task you need doesn't exist, add it rather than documenting a raw command here.
- `mise.toml`'s `[env]`: `COMPLEO_COMPLETION_DIR={{config_root}}/.completions` so a mise-activated shell (or `mise x -- ...`) writes into the project instead of the real `~/.local/share/compleo/completions` (`.completions/` is gitignored). `_.path = ["{{config_root}}/examples"]` puts the demo scripts (`greet`, `macros`) on `$PATH` by bare name, since their generated completions need that to work at all (see "Generating and serving a wrapped script's own completion" above).

## Release & CI

- `.goreleaser.yml`: builds `cmd/compleo` for linux/darwin × amd64/arm64. Relies on GoReleaser's implicit default ldflags (see "Versioning" above) rather than declaring its own.
- `.github/workflows/ci.yml`: `check-ubuntu`/`check-macos` (literal `runs-on`, **not** `strategy: matrix` — see below) run `mise run check`; `release-check` validates `.goreleaser.yml` on every PR.
- `.github/workflows/release.yml`: runs GoReleaser on `v*` tag pushes.
- `.github/dependabot.yml`: weekly `gomod` + `github-actions` update PRs.
- **act gotchas** (all handled in `mise-tasks/ci-local`, don't re-break them):
  - act doesn't read Docker contexts; `DOCKER_HOST` must be set explicitly from `docker context inspect --format '{{.Endpoints.docker.Host}}'`.
  - `runs-on: ${{ matrix.os }}` under a `strategy.matrix` races in act when multiple matrix entries evaluate the expression concurrently (a shared-YAML-node mutation bug in act's `EvaluateYamlNode`) — why `ci.yml` uses two literal jobs instead of a matrix over `os`.
  - `--container-daemon-socket -` disables bind-mounting the Docker socket into job containers — required under any VM-based runtime (Colima, Rancher Desktop), where the host socket path isn't valid inside the VM.
  - `act push` runs every workflow with a `push` trigger, ignoring `release.yml`'s `tags: ["v*"]` filter — `ci-local` scopes to `-W .github/workflows/ci.yml` so it doesn't also attempt a real `goreleaser release`.

## Conventions

- Format with `gofmt`; run `go vet` and the configured linter before finishing a change.
- Prefer separate top-level `Test...` functions over table-driven tests, even when it means similar-looking functions repeated — this project's explicit preference, not a Go-wide default.
- Use `testify` (`require`/`assert`) in tests rather than hand-rolled `if err != nil { t.Fatalf }` checks. `require` for preconditions the rest of the test depends on; `assert` for independent checks that should all get reported even if one fails.
- The emitted zsh code is the main contract. Cover it with golden-file tests, and execute the output under `zsh -f` in at least some tests.
- Quoting must be rigorous: arguments can contain spaces, quotes, `$`, backticks, and newlines. Never build emitted shell by naive string concatenation; use one tested quoting function.
- Current package split: `internal/spec` (YAML parsing, types, and building the spec's cobra/completion/usage tree — usage can't be its own package without an import cycle, since it needs `spec.Command`), `internal/parse` (binds a parsed command line to a `Result`), `internal/shells` (per-shell emitters; zsh is `internal/shells/zsh`), `internal/generate` (the `generate`/`_COMPLEO_GENERATE_NAME` completion-file-writing flow), `internal/cmdutil` (dependency-free leaf: `CompletionDir`, `WriteCompletionFile`, env var name constants). Each still testable alone.
- Keep code comments short — one line where possible. Explain the non-obvious *why*, not a paragraph of it.
