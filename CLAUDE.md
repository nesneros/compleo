# compleo

A Go tool for zsh scripts. One spec file is the single source of truth for three things:

1. **Parsing** the script's command line
2. **Usage / help message**
3. **zsh completion**

The script calls compleo near the top; compleo parses `"$@"` and prints zsh code that the script `eval`s to set variables. Completion is generated from the same spec, so the three never drift apart.

## Status

Early design phase, but the core pipeline is implemented: `go.mod` at `github.com/nesneros/compleo`, `cmd/compleo/`, `internal/spec`, `internal/parse`, `internal/zsh`, `internal/generate`, `internal/cmdutil`, mise tooling, GoReleaser + GitHub Actions CI. Spec parsing, cobra/usage building, command-line parsing, zsh emission, and completion generation (both compleo's own and a wrapped script's) all work end to end — see `examples/greet`, `examples/extensions` (every compleo-added `positionals:`/`type:` combination), and `examples/macros`. Treat anything under "Open questions" as undecided and ask before choosing.

## Design decisions

- **Language:** Go.
- **Target shell:** zsh only. Emit zsh syntax directly; no bash/POSIX compatibility needed. Design should stay open to extension with e.g. bash later.
- **Completion:** built on carapace, for its rich completion actions (hosts, ssh keys, brew formulae, files, ...). Spec fields for completion stay as close as possible to the carapace-spec format.
- **Macro names:** use the same names as carapace-spec/carapace-bin (e.g. `$files`, `$carapace.tools...`) — don't duplicate that naming knowledge.
- **A flag's/positional's own `completion:` lives right on its own `flags:`/`positionals:` entry, not in a separate top-level section** (changed from an earlier design matching plain carapace-spec's own shape): plain carapace-spec keys a command's completion actions by flag name/positional index in a command-level `completion: {flag: {...}, positional: [...]}` map, disconnected from the flag's/positional's own definition. That split exists in carapace-spec/carapace-bin for a structural reason that doesn't apply to compleo: carapace's primary job is retrofitting completion onto a command *that already exists* — a CLI built with its own `pflag.FlagSet`, which has no completion field at all (pflag predates carapace) — so completion can only be bolted on afterward as a separate, name-keyed registration, mirroring how cobra itself does shell completion (`RegisterFlagCompletionFunc`, also a side map keyed by name, not a method on the flag). compleo isn't retrofitting anyone else's command — it builds the cobra tree itself from its own `Flag`/`Positional` structs (see the duplication bullet below) — so there's no reason to keep the split: `Flag.Completion`/`Positional.Completion` (`internal/spec/flag.go`/`command.go`) hold the same action-expression value (`["$files"]`, or a plain list of literal values — unchanged from plain carapace-spec's own `completion:` value shape) directly on the entry it completes, and `Command.toCarapace()`'s `flagCompletions`/`positionalCompletions` gather them back into carapace-spec's own name-keyed/index-keyed shape right before handing off to `ToCobraE()`. `Completion` (the struct) keeps only `positionalany`/`dash`/`dashany` — the handful of completion slots with no single flag/positional to live on.
  - **Breaking change, deliberate:** a spec's old top-level `completion: {flag: ..., positional: ...}` shape now hard-errors under `decodeYAML`'s `KnownFields(true)` (those two keys no longer exist on the `Completion` struct at all) — not silently ignored, not auto-migrated. Every spec in this repo (`cmd/compleo/spec.yaml`, every `examples/*`) was migrated in the same change that introduced this.
  - **Positional completion gets two behaviors flags don't need, both in `positionalCompletions`:** (1) the built index-keyed list is trimmed of trailing not-completed entries (returning `nil` outright if none are completed) — carapace's own `storage.go` (`getPositional`) treats *any* list entry at an index, even an empty one, as that index's actual completion, so a naive full-length list with nil gaps would silently shadow `completion.positionalany`/cobra's default for every position on a command that simply has `positionals:` declared with no completion on any of them. A gap *before* a later declared completion still can't be avoided this way (same inherent limitation plain carapace-spec's own index-keyed list always had) — only a *trailing* run is trimmed. (2) a trailing **variadic** positional's own completion is also used as `completion.positionalany` when the command doesn't declare one explicitly (explicit always wins, same precedence rule enum derivation already uses) — carapace's index-keyed list has no way to say "and every word after this one too", so without this fallback only the variadic's first word would ever get its declared completion.
- **Parsing and usage are extensions:** carapace-spec's flags have `required`/`default` but nothing for flag *types* beyond string/[]string/bool/count, and nothing structured for positionals at all.
- **`spec.Command` duplicates carapace-spec's `command.Command`, rather than embedding/wrapping it** (changed from an earlier design): `internal/spec/command.go` declares `Command` as its own independent struct — same field names/YAML tags as `command.Command`, but not the same Go type — and `internal/spec/flag.go` likewise declares compleo's own `Flag`/`FlagSet` instead of reusing `command.Flag`/`command.FlagSet`. `toCarapace()` converts compleo's `Command`/`FlagSet`/`Flag` into carapace's own equivalents at the one point that still needs them: handing off to carapace-spec's `ToCobraE()` to actually build the cobra tree (that part is still fully reused, not reimplemented). The reason to duplicate rather than embed: embedding only lets compleo *add* fields the carapace type doesn't have (which is how `Positionals`/`FlagTypes` worked before) — it can't add a field onto a carapace-owned struct like `Flag` itself, forcing any per-flag extension into a side-channel map keyed by flag name, disconnected from the flag's own definition. `Flag.Type` (replacing the old `FlagTypes map[string]Type`) is the first case of this; `Flag.Completion`/`Positional.Completion` (see the completion co-location bullet above) are another; a future per-flag/positional validation attribute (see Open questions) would extend `Flag`/`Positional` the same direct way. `Positional` was already compleo's own type with nothing to reuse, so it's unaffected.
  - Duplicating `Flag`/`FlagSet` means compleo's `FlagSet.UnmarshalYAML` (`internal/spec/flag.go`) also duplicates carapace's own (unexported, no extension hook) flag-key parsing (`-c, --count=*!` shorthand-and-modifier syntax) rather than reusing it, plus recognizes one more key in a flag's object form, `type:`, alongside carapace's own `description`/`nargs`/`default`. A spec with a flag's `type:` still decodes fine under plain carapace-spec/carapace-bin — their `FlagSet` decoder already tolerates unrecognized keys in the object form, silently ignoring `type:` rather than erroring.
  - Side effect, not the goal: `Command.UnmarshalYAML` (which only existed to re-decode `commands:` into `[]Command` instead of the embedded struct's own `[]command.Command`) is gone too, since a plain `Commands []Command` field decodes recursively on its own. Its removal means `decodeYAML`'s `decoder.KnownFields(true)` now actually reaches every level of the document for the first time — previously, `Command` being its own `yaml.Unmarshaler` meant the *whole* document (root included) was decoded via that unmarshaler's own fresh `value.Decode(...)` call, which doesn't inherit the outer `Decoder`'s `KnownFields` setting, silently defeating it everywhere. Confirmed via `TestParseYAMLRejectsUnknownTopLevelKey` and by re-running `compleo validate`/`--help` against every real spec in the repo after this change.
- **`Type` is an interface, one concrete struct per kind** (`internal/spec/type.go`; changed from an earlier design where `Type` was a bare string const and `enum`'s `Values` was a side-field bolted onto `Flag`/`Positional` directly): `StringType{}`/`IntType{Min, Max *int}`/`FloatType{Min, Max *float64}`/`BoolType{}`/`DurationType{}`/`PathType{}`/`EnumType{Values []string}`, each implementing `Validate(s string) error` and an unexported `hint() string` (what `--help`'s backtick-quoted type hint shows). The reason to make it a sum type rather than keep adding fields to a flat struct: `Min`/`Max` only mean anything for `int`/`float`, `Values` only for `enum` — a flat struct accumulates fields that are meaningless for every kind but one, the same side-channel smell `spec.Command`'s own duplication (see above) was fixed for one level up. `Flag.Validate`/`Positional.Validate` are now thin, identical one-line wrappers (`if f.Type == nil { return nil }; return f.Type.Validate(s)`) — the nil-check matters because a zero-value `Flag{}`/`Positional{}` (e.g. a map lookup miss, or Go test code not going through YAML decode) has a nil interface, and calling a method on a nil interface panics (a plain type-assertion like `f.Type.(EnumType)`, used by `flagCompletions`/`positionalCompletions` below, is nil-safe on its own and needs no such guard).
  - YAML: a bare string (`type: int`) is shorthand for the object form with nothing but that kind (`type: {kind: int}`) — decoded by `decodeType(v any) (Type, error)` in `type.go`, called from both `FlagSet.UnmarshalYAML` (`internal/spec/flag.go`) and `Positional`'s own new `UnmarshalYAML` (`internal/spec/command.go` — previously had none, relying on plain struct tags; needed one now since an interface field has no natural YAML shape of its own, and this was also the chance to give `Positional` the same manual-map-decode-plus-known-key-check rigor `FlagSet` already had, rather than silently tolerating a typo'd key). No new top-level key on the flag's own object form — `min`/`max`/`values` all nest inside `type: {...}`, not alongside `description`/`nargs`/`default`.
  - `toCarapace()`'s `flagCompletions`/`positionalCompletions` still auto-populate an `EnumType` flag's or positional's own `Completion` from its own `Values` when it has none of its own — declare the list once, get both parse-time validation and Tab-completion, instead of repeating it under both `flags:`/`positionals:` and `completion:`. An explicitly declared `Completion` for that same flag/positional always wins over the derived one (e.g. to add per-value descriptions or styling) — this only ever fills a gap, never overrides. (Flags and positionals are symmetric here now that both own their own `Completion` field directly — an earlier version of this derivation only covered flags, back when a positional's completion still lived in carapace-spec's index-keyed top-level list with no single slot of its own to derive into.) `IntType`/`FloatType`'s `Min`/`Max` get no such derivation at all: the closest macro, carapace-bin's `$carapace.number.Range(start,end)`, needs the separately-installed `carapace` binary (see `examples/carapace_bin_macros`'s own design-decision bullet below) — deriving completion from it would mean a bounded int/float flag's *completion* silently stops working without that binary even though *validation* still works fine, an asymmetry `enum`'s free, dependency-free literal-values derivation doesn't have. Left undone; declare `completion:` yourself if you want it for a bounded numeric flag.
  - `IntType`/`FloatType`'s `Validate`/`hint` share their actual bound-checking and hint-formatting logic via two small generic functions, `checkRange[T cmp.Ordered]`/`rangeHint[T cmp.Ordered]` — only the string-parsing step (`strconv.Atoi` vs `strconv.ParseFloat`) and the error's value-formatting verb differ between the two types, so duplicating the rest would just be copy-paste. Deliberately two plain structs with generic *helper functions*, not one generic struct embedded into both (`IntType{numericRange[int]{...}}`) — Go doesn't promote an embedded generic struct's fields into the outer type's composite-literal syntax, so `IntType{Min: &x, Max: &y}` (the ergonomic form every test and example already uses) would stop working. The hint includes the bounds, not just the bare kind name, mirroring `enum`'s own hint — `--port int 1-65535` (both), `--port int >=1` / `--port int <=65535` (one), `--port int` (neither), matching the YAML's own `min`/`max` wording.
  - The type hint in `--help` shows the enum's own values (`` (`red|green|blue`) ``) instead of the literal word `enum`, since that's what's actually useful to a human — plain type names (`` (`int`) ``) are unaffected.
- **Result delivery:** the Go program prints a zsh script; the calling script `eval`s it. Parsed values go into an associative array.
- **Architecture:** spec is built into an in-memory `cobra.Command` at runtime via `spec.Command`'s private `toCarapace().ToCobraE()`. Not carapace's `--codegen`: that writes static per-command `.go` stubs for an offline compile step, which doesn't fit "one generic binary, arbitrary spec read fresh every invocation."
- **Parsing engine:** cobra/pflag via `ToCobraE()`, not a custom parser. Cobra/pflag only register real flags for `string`/`[]string`/`bool`/`count`; other declared `type:` values (a flag's or a positional's) are plain strings to them, so `internal/parse`'s `bindFlags`/`bindPositionals` validate those itself via `spec.Flag.Validate`/`spec.Positional.Validate` — the only place an invalid type declaration is ever caught. A flag's effective spec.Flag (needed for its Type and, for an enum, Values too — not just the type name) is resolved per (sub)command in `internal/parse`'s `wireCommand`: its own `Flags`/`PersistentFlags`, merged with whatever its ancestors declared on *their* `PersistentFlags` (not their own `Flags` — those aren't inherited) — matching cobra's own behavior of merging an ancestor's persistent flags into a subcommand's `cmd.Flags()`. Positional arity/required-ness/binding is entirely `internal/parse`'s own (cobra's `Args` is always `cobra.ArbitraryArgs`). A typed flag's `--help` shows its declared type (e.g. `` (`int`) ``) appended to the description by `Flag.toCarapace()` (folded in per-flag now, not a separate post-processing pass over the whole `FlagSet`), since pflag's `UnquoteUsage` looks for a backtick-quoted segment and uses it as the displayed type instead of `flag.Value.Type()`.
  - **Bug fixed while building `examples/extensions`:** `bindFlags` validates every registered flag via `cmd.Flags().VisitAll`, not just ones the user actually typed — an *optional* typed flag with no `default:` registers at pflag's own zero value (`""` for a string-kind flag), which isn't a valid `int`/`float`/`bool`/`duration`/`enum` either, so it failed validation on every single invocation that didn't happen to set it, even though the user never touched it. Fixed by only validating when `f.Changed` (the user set it) or `spec.Flag.Default != ""` (the spec author declared one, worth validating too, to catch a bad default) — an unset, no-default typed flag is simply never validated now. `examples/greet`'s only typed flag (`--times`) happened to always declare a `default: "1"`, masking this for the entire rest of the session; `examples/extensions`'s `--ratio`/`--enabled` (typed, optional, no default) surfaced it immediately. Covered by `TestParseUntypedUnsetOptionalTypedFlagDoesNotFailValidation`/`TestParseInvalidDeclaredDefaultOnTypedFlagStillFails`.
- **Spec delivery at runtime:** the target script's spec is read from compleo's stdin, not a file-path argument — lets the calling script supply it as a heredoc, inline variable, or an external file (`compleo up < "$spec_file"`, no `cat` needed). Consequence: in `parse` mode, compleo's wrapped-script argv is entirely the wrapped script's own arguments.
  - Inline heredoc vs. a separate YAML file isn't something compleo picks for you — it's purely the calling script's own choice, since either way is just "what's on stdin" to compleo. `examples/carapace_bin_macros` uses an external file (`carapace_bin_macros.yaml`, next to the script) specifically because that spec is large; every other example inlines its (much shorter) spec directly in the script via a heredoc.
  - **`parse`/`up`/`validate` all fail fast instead of blocking when stdin isn't piped, unlike ordinary Unix tools:** `main()`'s `isPiped(os.Stdin)` (`cmd/compleo/main.go`) checks whether stdin is a pipe/redirect vs. an interactive terminal; `run()`'s one shared block (right before its `switch cmdName`, covering all three since all three need the same `io.ReadAll(in)`) returns an immediate error when `!piped`. The usual Unix convention is to block on stdin until EOF (`cat`, `grep`), but none of these three have a legitimate interactive use case either — `validate` included, despite being a standalone subcommand a human might reach for directly, since `compleo validate` with nothing piped to it is still never something to wait on. Blocking would only ever mean something's wrong (a forgotten heredoc, a bad invocation, a missing redirect), and for `parse`/`up` specifically, inside a command substitution that looks like a silent hang with no prompt or visible cue, not an obvious "waiting for input."
- **compleo's own CLI vs. `parse` mode:** `parse` is a real subcommand in `cmd/compleo/spec.yaml`, like `version`/`validate`/`activate` — flags: `--name`; positionals: one variadic `args`, absorbing the wrapped script's entire argv. It's dispatched through the exact same generic path as every other compleo subcommand (`parse.Parse(ownCmd, ownSpec, args)`, then `switch result.Path[last]`); `run()`'s `case "parse":` pulls `result.Positionals["args"].Values` and `result.Flags["name"].String` and calls `runEmit` or `generate.Generate` depending on whether `_COMPLEO_GENERATE_NAME` is set (see below). (`--dump`, an earlier debugging flag that tee'd the result to stderr, was removed — no caller left needing it.)
  - `"--"` is optional: it's only needed to disambiguate a wrapped script's own flag from one of compleo's own `parse`-level flags (`--name`, cobra's auto `--help`) — e.g. `compleo parse -- --name` makes `--name` the wrapped script's own. With no collision, `compleo parse world` works with no `--`. This is ordinary pflag behavior (`parseArgs` stops interpreting flags at a bare `--`), not hand-rolled parsing — and it means `compleo parse --help` (before any `--`) shows `parse`'s own flag docs for free.
  - A variadic positional with zero bound values comes back as `nil` (not `[]string{}`) from `bindPositionals`; `parse.Parse` panics on a nil argv. `run()`'s `case "parse":` normalizes `nil` to `[]string{}` before dispatching, since a wrapped script with zero of its own arguments is common, not an edge case.
  - `version`/`validate`/`activate`/`generate`/`up` are subcommands on compleo's own CLI, not root flags, so they read the same as any other spec subcommand. There's no separate `help` subcommand, only cobra's own `--help`/`-h`, available on every (sub)command — compleo doesn't fight cobra's automatic `--help` (no documented per-command opt-out exists), so `compleo validate --help` works too, same as `git commit --help`.
  - `--help` is intercepted by cobra before `RunE` runs. `internal/parse`'s `helpRequested` recurses the whole command tree checking `Flags().Changed("help")` and `Parse` sets `Result.HelpRequested` from it right after `cmd.Execute()` succeeds — this can't be inferred from `Path`/`Flags` being empty, because cobra converts `flag.ErrHelp` to a `nil` error before `Execute()` returns, so success alone doesn't say whether the matched command's `RunE` actually ran. A genuine `parse.Parse` error and `HelpRequested` can never both be true.
- **Wrapped-script completion install location:** `compleo activate` prints zsh that does `fpath+=(...)` — meant to run in `.zshrc` **before** `compinit` (`compinit`'s directory scan only sees what's already on `$fpath` when it runs). The directory (`cmdutil.CompletionDir()`) is `$COMPLEO_COMPLETION_DIR` if set, else `${XDG_DATA_HOME:-~/.local/share}/compleo/completions`; creating it is a side effect of `cmdutil.WriteCompletionFile`'s own `os.MkdirAll`, run server-side as part of `activate` itself, not something the printed zsh does.
  - `activate` also writes compleo's own completion to `cmdutil.CompletionDir()/_compleo` via `cmdutil.WriteCompletionFile`, which skips the write when content is unchanged — needed because `activate` may run on every shell startup, and touching the file every time would bump the directory's mtime, which is what makes `compinit` rescan `fpath` instead of trusting its `.zcompdump` cache. This depends on `zsh.Completion`/`Emit` being deterministic for identical input (covered by `TestCompletionIsDeterministic`).
  - No extra "make this autoload" step is needed beyond the directory being on `$fpath`, *if* `compinit` still runs afterward (the documented order): it reads each file's `#compdef` first line at scan time, and only runs the body lazily on that command's first Tab-press. But if `activate` runs in an already-initialized shell (`compinit` already ran once, so adding to `$fpath` alone changes nothing for *this* session), `zsh.EmitActivate` also emits a guarded `autoload -Uz <dir>/* ; (( $+functions[compdef] )) && for f (<dir>/*) compdef ${f:t} ${f:t:s/_//}` — guarded because `compdef` doesn't exist as a command until `compinit` has run once (confirmed empirically), so this must be a no-op in the documented before-`compinit` flow, not an error. `dir` is never empty (`_compleo` is always there), so the glob always matches.
  - `EmitActivate` also defines a `compleo() { command compleo "$@" }` shell function — run in `.zshrc`, so it lands in the interactive shell itself, not a subprocess. Today it's a transparent passthrough (the `command` is load-bearing: without it, calling `compleo` from inside the function would recurse into itself instead of reaching the real binary); the point of having it at all is that a shell function, unlike every other way compleo runs, can eventually also modify the calling shell's own state (e.g. its env), which nothing else here can do. Every other invocation (`up`'s nested `eval "$(compleo parse ...)"`, a Tab-press's `_carapace` dispatch) still goes through this function transparently once defined, since zsh resolves a bare command name to a function before a `$PATH` binary.
- **Quoting:** `internal/zsh.Quote` (single-quote style, escaping embedded `'` via `'\''`) is the one quoting function used everywhere zsh is emitted.
- **`internal/zsh.Emit`:** a fixed associative array named `compleo` holds every scalar flag's/positional's value (`compleo[name]=value`); a repeatable flag or variadic positional gets its own real zsh array (`compleo_<name>=(...)`) instead, since assoc-array values are scalars only. Booleans are always present as `"true"`/`"false"` (not presence/absence); count flags render as a plain integer string.
  - Assoc-array keys must stay unquoted (bareword) — `compleo['loud']=x` stores the literal key `"'loud'"`, not `"loud"`. Only the value needs `Quote()`; names come from the spec, always simple tokens.
  - A separate array's variable name is sanitized (every non-`[A-Za-z0-9_]` char, e.g. a flag's `-`, becomes `_`), not quoted — a literal hyphen in a zsh variable name breaks even referencing it later (`${my-array[1]}` parses as `${param-default}`, not a subscript). This can collide two differently-sanitized names onto one array; compleo doesn't guard against it — keep spec names distinct.
  - Iteration over `result.Flags`/`result.Positionals` is sorted (`sortedKeys`) for deterministic output, which `activate`'s skip-if-unchanged write depends on.
- **`--help` in `parse` mode:** cobra's `HelpFunc` writes straight to `OutOrStdout()` — the same stream the wrapped script evals as zsh. `runEmit` buffers the wrapped `cmd`'s output (`cmd.SetOut(&helpBuf)`), and if `HelpRequested`, emits `zsh.EmitHelp(helpBuf.String())` instead of `zsh.Emit`. `EmitHelp` wraps the text as `print -r -- <Quote(text)>\nexit 0` — `exit`, not `return`, since `return` inside `eval`'d code only exits an enclosing function if the script wraps its logic in one. `cmd.SilenceErrors`/`SilenceUsage` (set on the wrapped `cmd` too) stop cobra from also writing its own `Error:`/`Usage:` straight to the real stderr alongside compleo's own reported error.
- **Parse errors in `parse` mode are encoded into the output, not returned as a Go error:** `zsh.EmitError(name, err)` formats `"name: err"` itself, prints `print -u2 -- <Quote(...)>\nexit 2`, and returns nil. Exit 2 specifically (not `main()`'s generic exit 1), so a script checking `$?` can tell the two apart. `name` is the spec's `name:` field, not the real `$0` (compleo never sees it — `argv` is literally `"$@"`; `examples/greet` interpolates `${0:t}` into its own `name:` for this). This means a wrapped script needs only `eval "$(compleo parse -- "$@" <<SPEC ... SPEC)"`, no separate `|| exit $?` — eval'ing the output alone stops the script. Gap this doesn't cover: if compleo itself fails to even launch, there's no output to eval at all — an explicit exit-code check is the only way to catch that.
- **Env var names are Go constants, not string literals:** `internal/cmdutil/env.go` defines `EnvCompletionDir`/`EnvGenerateName`/`EnvSpecFile`/`EnvDebugLog` (the `COMPLEO_*`/`_COMPLEO_*` names) — every `os.Getenv`/`os.Setenv`/`cmd.Env` read or write, and `zsh.WrappedCompletion`'s emitted `local -x <name>=...`, references the constant, so the Go side setting one and the Go side reading it (or, for `EnvSpecFile`, the zsh compleo itself emits) can't drift apart from a typo. `cmdutil` is a dependency-free leaf package already imported by `cmd/compleo`/`internal/generate`; `internal/zsh` also imports it now, just for these constants.
  - **Naming convention: a leading `_` marks internal plumbing.** `COMPLEO_COMPLETION_DIR` is the one stable, user-facing config knob — a user sets it once in `.zshrc`/`mise.toml` and never thinks about it again. Every other one (`_COMPLEO_GENERATE_NAME`, `_COMPLEO_SPEC_FILE`, `_COMPLEO_DEBUG_LOG`) is compleo setting something for compleo to read back, or an internal mechanism a user can still reach for by hand (triggering `generate` mode, turning on debug logging) rather than a durable setting — same convention Click uses for its own `_FOO_COMPLETE`, which `_COMPLEO_GENERATE_NAME`'s own by-hand-settable, mere-presence-triggers-generate-mode role already deliberately mirrors (see below).
- **`_COMPLEO_DEBUG_LOG`:** a second, opt-in error channel for the one invocation whose real stderr a caller unconditionally discards — a live Tab press's `_carapace` dispatch, via carapace's own generated `xargs ... 2>/dev/null` (carapace's template, not compleo's choice; patching it is out of scope). `main()`'s `logDebug` appends `<RFC3339 timestamp> args=<the exact argv> <error>\n` to the path this names, for *any* top-level error, not just `_carapace` — simplest to apply once, at the same place stderr already gets the message, rather than special-case which subcommand is running. Best-effort and silent on its own failure (bad path, unwritable dir, ...): a debugging aid must never become a second point of failure for compleo's primary error reporting, which already happened correctly via stderr/exit code regardless of whether this is set.
  - Must be a real file, not `/dev/stderr` — confirmed empirically. `os.OpenFile("/dev/stderr", ...)` succeeds and writes fine on its own, but in the one scenario this exists for, the calling shell already redirected its own fd 2 to `/dev/null` *before* compleo even started, so `/dev/stderr` resolves to that same `/dev/null` by inheritance — writing to it is exactly as invisible as the error compleo already (correctly) sent to its own stderr. Outside that scenario (stderr not already redirected), it would just duplicate the line `main()` already prints.
- **`internal/spec`'s API surface:** `ParseYAML` decodes and builds the cobra tree in one call — the one entry point everything uses. `decodeYAML`/`toCarapace`/`Apply` are private. `ParseYAML(data string, name string)` takes the spec as a plain `string`, not an `io.Reader`: every real caller already has the full spec in memory before calling it (an embedded `[]byte`, something already read via `os.ReadFile`/`io.ReadAll`, or a test's string literal) — accepting a reader bought nothing but an extra `bytes.NewReader(...)`/`strings.NewReader(...)` wrap at most call sites, for a document that's always small enough to just hold entirely. `decodeYAML` still wraps `data` in a `strings.NewReader` internally, since `yaml.Decoder.KnownFields(true)` (needed for strict unknown-field rejection) is only available via `yaml.NewDecoder(io.Reader)`, not the package-level `yaml.Unmarshal([]byte, ...)`.
- **`compleoCmd` panics rather than returning an error on an invalid embedded `spec.yaml`:** it's built in via `go:embed`, so a parse failure there is a bug, not a runtime condition — unlike `runCarapace`/`runParse`, which parse specs genuinely coming from outside and return ordinary errors.
- **YAML library pin matters:** must use `gopkg.in/yaml.v3`, not `go.yaml.in/yaml/v3` — `spec.Command`'s `Run command.Run` field reuses the pinned `carapace-sh/carapace v1.16.3`'s `command.Run`, which has a custom `UnmarshalYAML` method tied to that specific package's `*yaml.Node` type; the other library's decoder silently won't find it. (`command.FlagSet`/`command.Flag` no longer matter for this pin — compleo decodes its own `Flag`/`FlagSet` now and only ever *constructs* carapace's, in `toCarapace()`, never decodes YAML into them.) Carapace migrates to `go.yaml.in/yaml/v3` after this tag — revisit this pin together.
- **Versioning:** follows carapace-bin's pattern — `version`/`commit`/`date` vars in `cmd/compleo/version.go`, populated by GoReleaser's default ldflags. `versionString()` appends `(date) [commit]` when `version` contains "SNAPSHOT", or when `version` is still `dev` and both `date`/`commit` are set.
- **Canonical carapace org & versions:** the project lives at `carapace-sh`; `rsteube/*` repos just redirect there. Pinned: `carapace-spec v1.9.0`, `carapace v1.16.3`, `cobra v1.10.2`, `pflag v1.0.10` (see next bullet — effectively replaced by the pinned fork at runtime).
- **Full flag-syntax support (resolved — adopted the fork):** `go.mod` has `replace github.com/spf13/pflag => github.com/carapace-sh/carapace-pflag v1.3.0`. Without it, a shorthand-only flag (`-v:`, no `--verbose`), a multi-letter single-dash flag, or an `nargs`-consuming flag (`--pair=: {nargs: 2}`) all silently fail to register — not an error, just absent: gone from `--help`, and typing it gets a generic "unknown flag" as if it were never declared. Root cause: carapace-spec's `addFlagTo` *does* detect this and returns an error, but its caller (`addFlags`) discards the return value; deeper still, the fork-specific registration methods it calls (`StringS`, `BoolN`, ...) are invoked through a reflection shim (`fork.go`'s `flagSet.call`) that silently no-ops when the real `*pflag.FlagSet` doesn't have them, rather than panicking. The fork is a drop-in `replace`, same `spf13/pflag` import path, no code changes needed anywhere in compleo — confirmed via `TestParseShorthandOnlyFlagParses`/`TestParseNargsFlagConsumesMultipleArgs` and by re-running every example script end to end.
- **Generating and serving a wrapped script's own completion:** there is no separate mode env var — `_COMPLEO_GENERATE_NAME`'s mere presence (any non-empty value) is both the name and the trigger. `main()` reads it once via `os.Getenv` and threads it down as a plain `generateName string` parameter through `run`/`runParse` (not a hidden `os.Getenv` read deeper in the call chain); `runParse` calls `generate.Generate` when it's non-empty, `runEmit` otherwise. It changes what the wrapped script's existing, unconditional `eval "$(compleo parse -- "$@" <<SPEC ...)"` line does, with no mode-aware logic needed in the script itself:
  - unset (`""`): parse `"$@"` against the piped spec, as above (`runEmit`).
  - `generate`: build the wrapped script's completion snippet (`zsh.WrappedCompletion`) and write it to `cmdutil.CompletionDir()/_<name>` (skip-if-unchanged, like `activate`'s own `_compleo`), then report success as self-exiting zsh (`zsh.EmitGenerated`). Triggered by hand: `_COMPLEO_GENERATE_NAME=greet ./greet` once, or after a spec change — same mechanism-you-can-also-type-by-hand role Click's own underscore-prefixed `_FOO_COMPLETE=zsh_source foo` plays, which is exactly why `_COMPLEO_GENERATE_NAME` carries the same leading `_` rather than being the one plain `COMPLEO_*` config knob.
    - `EmitGenerated`'s message is just a one-shot activation hint for the current shell (a new shell picks up the file for free, since `compinit` rescans `$fpath` at startup): `"To activate completion for <name> in this shell, run: autoload -Uz _<name> && compdef _<name> <name>"` — advice for the user to run, not something compleo can do itself (a subprocess can't modify its parent shell's state). Must autoload `_<name>` (the file's own name), not `_<name>_completion` (the function `WrappedCompletion` defines inside it) — autoload resolves by filename, and only `_<name>` matches a real file; calling it is what actually defines and rebinds the inner function. Caught by `TestEmitGeneratedActivationHintActuallyWorksFromColdStart`.
  - There's no `complete` mode (an earlier design had one — superseded, see below). `runParse` only ever branches on `generate` vs. everything else now.
  - **No bulk orchestration (resolved — deliberately not doing this):** running `_COMPLEO_GENERATE_NAME=<name>` across every wrapped script a user has stays a manual, per-script step (`compleo generate <script>`, or by hand); nothing in `activate` or elsewhere ever discovers and regenerates them in bulk.
- **Live completion: the spec is embedded in the generated file, not re-fetched by re-running the wrapped script (resolved, was the main design still open earlier):** carapace's own generated snippet always re-invokes `uid.Executable() + " _carapace zsh"` — literally `compleo _carapace zsh <words>`, since `uid.Executable()` returns whatever binary is actually running, not the completed command. compleo reaches that with no spec on stdin at all. The earlier design worked around this by having `WrappedCompletion` patch that invocation to re-run the *wrapped script* instead (a since-removed "complete" mode, via `xargs <name>`), relying on the script's own heredoc to re-deliver its spec. That worked, but required the wrapped script to stay resolvable on `$PATH` forever, for every single Tab press — the root cause of several real "Tab does nothing, silently" bugs hit during development (always `2>/dev/null`-suppressed, so no error either). Superseded by embedding the spec directly:
  - `WrappedCompletion(cmd, name, specFilePath)` leaves carapace's own invocation untouched (so a Tab press dispatches straight to `compleo` itself, same as compleo's own self-completion already does) and instead injects one line right after `function _<name>_completion {`: `local -x _COMPLEO_SPEC_FILE=<Quote(specFilePath)>` — function-scoped and exported, so it reaches the `xargs`-spawned `compleo` child but never leaks outside the function (confirmed empirically).
  - **The spec's content lives in a companion file, not the env var itself** (revised from an initial design that embedded the full spec text as `COMPLEO_SPEC=<Quote(specYAML)>`): an env var is subject to OS-level size limits (`ARG_MAX`, shared across argv+envp, commonly ~1–2MB) with no graceful failure if hit; a file has no such practical limit. `generate.Generate` writes the raw, already-expanded spec bytes (whatever was actually piped to `compleo parse` at generate time) to `<completionDir>/.<name>.spec.yaml` via the same skip-if-unchanged `cmdutil.WriteCompletionFile` the `_<name>` completion file itself uses, then embeds *that path* (not the content) into the generated snippet. The leading dot matters: `EmitActivate`'s `autoload -Uz <dir>/*` globs every file in the completions directory, and zsh's bare `*` glob doesn't match dotfiles by default — without the dot, the companion file would get swept into that autoload loop as a bogus, harmless-but-wrong entry (confirmed empirically, `print -rl -- dir/*` only lists `_greet`, not `.greet.spec.yaml`). Same frozen-at-generate-time tradeoff as before: any shell expansion in the wrapped script's own heredoc (e.g. `${0:t}`, or a `$spec(${0:A:h}/...)` macro's path) has already happened by generate time, so regenerating is needed if the script or its spec changes or moves.
  - On the receiving end, `run()` checks `_COMPLEO_SPEC_FILE` *before* building compleo's own `ownCmd` tree, as soon as it sees `args[0] == "_carapace"`: if set, it reads the file with `os.ReadFile` and passes its content straight to `runCarapace`, which builds a *fresh* cobra tree from it and dispatches directly into that. If unset (compleo's own completion, or a legacy generated file), falls through to the existing `ownCmd`-based `_carapace` handling, unchanged.
  - **A spec whose own text doesn't declare name: gets it prepended into the companion file** (`generate.Generate`): `name: '<name>'\n` + `rawSpec`, making the file a complete, standalone spec — `runCarapace` just parses it with no name param, no filename parsing needed. Keyed off `declaredNamePattern` (`(?m)^name:`, a cheap regex on `rawSpec` itself — column-0-anchored so it doesn't match a subcommand's indented `name:`), not `sp.Name`: `sp.Name` may already be non-empty via `--name` even though `rawSpec`'s own text has no `name:` at all (true of `examples/greet`, which uses `--name="${0:t}"` and no `name:` field) — checking `sp.Name` instead was tried and found to miss exactly this case. A regex avoids the cost of a second full `spec.ParseYAML` just to tell them apart.
  - This also means the raw wire format carapace's `_carapace` writes needs no wrapping anymore: it goes straight into the generated completion function's own `lines="$(...)"` capture, the same way it already does for compleo's self-completion — there's no wrapped script in the loop anymore for a Tab press to accidentally `eval`. `EmitComplete`/`runComplete`/`modeComplete` are gone; nothing else used them.
  - Net effect: a wrapped script doesn't need `$PATH` at all for *using* its completion (every Tab press) — only, at most, for `compleo generate` itself. `mise.toml`'s `_.path` (adding `examples/` to `$PATH`) still matters for *generating* the demo scripts' completions, just no longer for using them afterward.
  - `compleo generate <script>` is a thin convenience subcommand (`generate.GenerateFor`): resolves `script` via `exec.LookPath`, then runs it as a subprocess with `_COMPLEO_GENERATE_NAME` set to the resolved name — exactly equivalent to typing `_COMPLEO_GENERATE_NAME=<name> <script>` by hand. Its `script` positional (renamed from `name`, which was confusing once a path became valid too) completes via `$compleo.scripts` (below), not carapace's generic `$executables`. Before executing, it checks `spec.IsCompleoScript(path)` (same check `$compleo.scripts` uses) and refuses otherwise — a basic sanity check, not a security boundary, since it only ever runs *something already found on `$PATH`*.
  - **`$PATH` isn't strictly required even for `generate`**: `script` can be a path (`compleo generate ./examples/greet`, or an absolute path) instead of a bare name — `exec.LookPath` resolves a path containing `/` directly, without consulting `$PATH` at all (confirmed in Go's source/docs). `_COMPLEO_GENERATE_NAME` is set from `filepath.Base(script)`, not `script` itself — it must be a bare name to match what the script's own `${0:t}` (or a hardcoded `name:`) computes; passing the whole path through unchanged used to make every such invocation fail with a spurious "spec declares name: ..., but ./examples/greet was invoked" mismatch (confirmed, then fixed).
  - **`name:` in the spec is now optional** (resolved): `generate.GenerateFor` passes the resolved name through as `_COMPLEO_GENERATE_NAME`, and `generate.Generate` uses it to fill in a missing `name:` — the common case for a wrapped script's own heredoc spec, since there's nothing to conflict with. If `name:` *is* declared and disagrees with the invoked name, `generate.Generate` fails outright (an error, not a silent override as an earlier design did) — generating under the wrong name would otherwise silently break Tab-completion for what's actually typed. Since `_COMPLEO_GENERATE_NAME` is now also what selects generate mode in the first place, this check applies every time generate mode runs, whether triggered via the `generate <script>` subcommand or set by hand.
  - Without a `name:` at all, `--help` still has to render *something*: `ParseYAML` sets `cmd.Use = "<script>"` when `sp.Name == ""`, right before `applySpec`/`wire` build the synopsis from it — otherwise cobra's `Name()` reads the empty `Use` as a blank first word, showing up as a stray extra space before `[flags]` in the printed "Usage:" line (and "help for this command" instead of naming anything). `<script>` is a placeholder, not a guess — compleo has no way to know the real invoked name here (no `_COMPLEO_GENERATE_NAME` authority outside the `generate` path, and compleo never sees `$0` either way).
  - **`compleo parse --name`** (typically `--name "${0:t}"`) lets a spec's heredoc drop `name:` and quote its delimiter (`<<'SPEC'`, no `$`/`` ` `` escaping anywhere in the body). `spec.ParseYAML(data, name)` takes the name directly: fills in a missing `name:`, errors on a mismatch with a declared one, before building `cmd` — so `cmd.Use`/`cmd.Name()` are already correct, no post-hoc rename needed. `runParse` just passes `--name`'s value through; every other caller passes `""`.
  - **`compleo up` — a subcommand that writes the `compleo parse --name=... -- "$@"` invocation for you**, so a script doesn't need to write `--name`/`--`/`"$@"` at all: `eval "$(compleo up <<SPEC ... SPEC)"` is the whole line. `run()`'s `case "up":` (`cmd/compleo/main.go`) just calls `zsh.EmitUp` with the already-read `rawSpec` (read by the shared block above, same as `parse`/`validate` — there's no separate `runUp` function), which prints `` eval "$(compleo parse --name="${0:t}" -- "$@" <<<%s)" `` with the spec embedded via `Quote()` as a `<<<` here-string (not a heredoc — no delimiter to pick, so no collision risk with spec content; `Quote()` already handles arbitrary content, confirmed with embedded `'`/`$`/`` ` ``). This means the `eval` the script runs expands into a *second* `eval "$(compleo parse ...)"`, invoking compleo again as a fresh subprocess — deliberate, not an oversight: `up` genuinely cannot know the calling script's own `$0`/`"$@"` itself (same reason `compleo` never sees them anywhere else), so the only way to fill them in is to emit code that references them directly in the *script's own* shell context, which requires a second, nested invocation.
    - `up` doesn't branch on `_COMPLEO_GENERATE_NAME` at all — confirmed empirically that it set on the wrapped script's own invocation still reaches the *inner* `compleo parse` call unchanged (plain env var inheritance across the nested `eval`/subprocess), so generate mode and normal parsing both work through `up` with zero mode-awareness needed in `EmitUp` itself.
    - `up` has no flags of its own — there's nowhere to attach one, since its only job is to transform stdin into the re-invocation text. `compleo parse --name="${0:t}" -- "$@"` directly is still there for anyone who needs finer control over the invocation itself.
    - An external spec file no longer needs a hardcoded `name:` either, now that `up` always supplies one: `eval "$(compleo up < "${0:A:h}/greet.spec.yaml")"` works with a nameless file (confirmed) — the earlier "name: has to be hardcoded for a file" caveat only applied to the plain `parse` form.
    - **A spec needing genuinely dynamic content** has two options, chosen by how much of the spec needs it. `examples/other_spec`'s `$spec(...)` macro needs one absolute path only the running script can compute (`${0:A:h}`) — with just that one thing dynamic, it keeps the heredoc unquoted (`<<SPEC`, not `<<'SPEC'`) straight into `up`, escaping the handful of literal `\$spec` mentions (same tradeoff `examples/greet`/`examples/macros` make the other way, just cheaper here since there's only one macro to escape). When *most* of the spec is static and only a small dynamic piece doesn't fit a quoted heredoc at all, capture the heredoc into a variable instead (`spec=$(<<'SPEC' ... SPEC)` — no `cat` needed, zsh reads a heredoc straight into a command substitution on its own, confirmed) and splice the dynamic piece in afterward via a plain zsh substitution (e.g. `${spec//@PLACEHOLDER@/${0:A:h}}`) before piping to `up` via `<<<`.
- **`$compleo.scripts` — compleo's first custom macro:** `internal/spec/macros.go` registers it via carapace-spec's `AddMacro`/`MacroN`. Narrower than `$executables` for `compleo generate <TAB>`: only offers executables on `$PATH` that look like they wrap compleo (shebang present, plus the literal word "compleo" in the first 4KB — `IsCompleoScript`, checked natively in Go, no `file` subprocess per candidate).
  - `actionScripts()` merges that filtered `$PATH` list with carapace's own `ActionFiles()` (`carapace.Batch(...).ToA()`), since `script` can be a path too (see above) — path candidates are unfiltered (carapace's path completion has no hook to hand it a content-based predicate), same tradeoff the `$files` macro already has.
  - `AddMacro("scripts", ...)` registers under the internal key `_.scripts`; `action.go`'s `ActionMacro` rewrites `$<running-binary-name>.foo` to `$_.foo` before lookup — so `$compleo.scripts` only dispatches when compleo is the running binary (true for every real invocation; tests use `$_.scripts` directly instead). Same mechanism carapace-bin uses for `$carapace.*`, not compleo-specific.
  - Macro registration is global, so any wrapped script's own spec can use `$compleo.scripts` too.
- **A carapace-bin macro's first path segment is the binary carapace-spec execs, not a category label — `examples/carapace_bin_macros.yaml` had this wrong almost everywhere** (bug hit live, not caught by `--help` since it only renders descriptions, never dispatches anything): `action.go`'s `ActionMacro`, for any `$X.Y...` that isn't `$<running-binary>.foo`, does `strings.SplitN(strings.TrimPrefix(s, "$"), ".", 2)` and execs `splitted[0]` as a literal command, passing `splitted[1]` as the macro path argument (`_carapace macro <splitted[1]>`). For the ~130 extra carapace-bin macros (shell/os/net/net.http/net.ssh/ps/fs/number/text/time/color/tools.\*), the real, fully-qualified name is always `carapace.<category>.<Name>` — a bare `$shell.Aliases` splits into exec target `"shell"` (no such binary) and macro arg `"Aliases"` (wrong path), rather than exec target `"carapace"` (the real, separately-installed completer binary) and macro arg `"shell.Aliases"`. The failure is near-silent: `ActionExecCommand`'s failure surfaces as a completion *message*, not a shell error — in practice `exec.LookPath("shell")` hits Go's `exec.ErrDot` safety check (refusing to implicitly run a same-named file resolved via `.` in `$PATH`), displaying literally "shell resolves to executable in current directory (./shell)" as if it were a candidate.
  - Fixed by cross-referencing every macro reference in the file against the real, installed carapace-bin's own catalog (`carapace _carapace macro` — add a trailing empty-string arg, e.g. `carapace _carapace macro shell.Aliases ""`, to also exercise dispatch, not just confirm the name is known): 97 entries needed only the `carapace.` prefix; 5 referenced a real category but a since-renamed/nonexistent name (fixed to the closest real equivalent, e.g. `fs.JarFileContents` → `fs.JarFileClasses`, `time.Weekdays` → `time.Days`); 12 referenced a macro that doesn't exist at all in that category (removed — no real substitute). CLAUDE.md's own illustrative example macro name (`$carapace.tools.git.branches`, in docs/spec.md) turned out to be equally fictional — fixed to a real one (`$carapace.tools.git.LocalBranches`).
  - Verify any *new* carapace-bin macro reference the same way before trusting it: get the real name from the installed completer's own catalog dump, don't guess a plausible-sounding one — a wrong name fails silently (a message, not an error) and `--help` can't catch it either, since rendering a description never dispatches the macro.

## Open questions (do not decide silently)

- `PathType` is still attribute-free — no way to require the value already exist, or be specifically a file vs. a directory. Resolving this is now just adding fields to `PathType{}` itself (e.g. `Exists bool`, `Must string`) and a `kind: path` case in `decodeType`'s attribute reading, the same shape `IntType`/`FloatType`'s `Min`/`Max` and `EnumType`'s `Values` already use — not a new mechanism, just not written yet. A more general per-type validation story (string pattern, etc.) beyond the kinds that already exist remains open.

## Things to verify before relying on them

- That current carapace-bin still generates `pkg/actions/actions_generated.go` the way v1.0.2 does.
- Resolved for a flag's own `type:`/`completion:` (plain carapace-spec's `FlagSet` decoder reads `description`/`nargs`/`default` from the object form and silently ignores any other key, so it tolerates both fine) and for `positionals:` (plain carapace-spec has no such top-level key at all, so it's simply never seen). A consequence of `completion:` moving onto the flag/positional itself, worth knowing even though it's tolerated the same way `type:` is: a plain carapace-spec/carapace-bin consumer handed the same file sees the flag's/positional's description and parsing behavior, but silently gets *no* completion for it at all (not just an ignored key) — unlike before, where `completion.flag`/`completion.positional` were plain carapace-spec fields a non-compleo consumer could still read and use. Still open in general: whether some other future compleo-only key, nested somewhere plain carapace-spec *does* otherwise recognize the surrounding structure, would also be silently tolerated — matters only if the same enriched spec file is ever meant to also be consumable directly by plain carapace-bin/carapace-spec.
- Importing `pkg/actions` links every action package; check the resulting binary size.

## Tooling: mise, not make

Use **mise** for tool versions and tasks. Do not add a Makefile.

- Tool versions (Go, golangci-lint, goreleaser, act) are pinned in `mise.toml` under `[tools]`.
- Simple tasks live in `mise.toml` under `[tasks.*]`; longer scripts are file tasks under `mise-tasks/` (e.g. `mise-tasks/ci-local`) with a `#MISE description=...` header — both run with `mise run <task>`.
- Tasks: `build`, `test`, `lint`, `fmt`, `check` (fmt check, vet, lint, test), `install`, `release-check` (`goreleaser check`, no build), `release-dry-run` (local snapshot build, no publish), `ci-local` (runs `ci.yml` locally via `act`, Docker required).
- If a task you need doesn't exist, add it rather than documenting a raw command here.
- `mise.toml`'s `[env]`: `COMPLEO_COMPLETION_DIR={{config_root}}/.completions` so a mise-activated shell (or `mise x -- ...`) writes into the project instead of the real `~/.local/share/compleo/completions` (`.completions/` is gitignored). `_.path = ["{{config_root}}/examples"]` puts the demo scripts (`greet`, `macros`) on `$PATH` by bare name, since their generated completions need that to work at all (see "Generating and serving a wrapped script's own completion" above).

## Release & CI

- `.goreleaser.yml`: builds `cmd/compleo` for linux/darwin × amd64/arm64. Relies on GoReleaser's implicit default ldflags (see "Versioning" above) rather than declaring its own.
- `.github/workflows/ci.yml`: `check-ubuntu`/`check-macos` (literal `runs-on`, **not** `strategy: matrix` — see below) run `mise run check`; `release-check` validates `.goreleaser.yml` on every PR.
- `.github/workflows/release.yml`: runs GoReleaser on `v*` tag pushes.
- `.github/dependabot.yml`: weekly `gomod` + `github-actions` update PRs.
- **act gotchas** (all handled in `mise-tasks/ci-local`, don't re-break them):
  - act doesn't read Docker contexts; `DOCKER_HOST` must be set explicitly from `docker context inspect --format '{{.Endpoints.docker.Host}}'`.
  - `runs-on: ${{ matrix.os }}` under a `strategy.matrix` races in act when multiple matrix entries evaluate the expression concurrently (a shared-YAML-node mutation bug in act's `EvaluateYamlNode`) — why `ci.yml` uses two literal jobs instead of a matrix over `os`.
  - `--container-daemon-socket -` disables bind-mounting the Docker socket into job containers — required under any VM-based runtime (Colima, Rancher Desktop), where the host socket path isn't valid inside the VM.
  - `act push` runs every workflow with a `push` trigger, ignoring `release.yml`'s `tags: ["v*"]` filter — `ci-local` scopes to `-W .github/workflows/ci.yml` so it doesn't also attempt a real `goreleaser release`.

## Conventions

- Format with `gofmt`; run `go vet` and the configured linter before finishing a change.
- Prefer separate top-level `Test...` functions over table-driven tests, even when it means similar-looking functions repeated — this project's explicit preference, not a Go-wide default.
- Use `testify` (`require`/`assert`) in tests rather than hand-rolled `if err != nil { t.Fatalf }` checks. `require` for preconditions the rest of the test depends on; `assert` for independent checks that should all get reported even if one fails.
- The emitted zsh code is the main contract. Cover it with golden-file tests, and execute the output under `zsh -f` in at least some tests.
- Quoting must be rigorous: arguments can contain spaces, quotes, `$`, backticks, and newlines. Never build emitted shell by naive string concatenation; use one tested quoting function.
- Current package split: `internal/spec` (YAML parsing, types, and building the spec's cobra/completion/usage tree — usage can't be its own package without an import cycle, since it needs `spec.Command`), `internal/parse` (binds a parsed command line to a `Result`), `internal/zsh` (emits the script), `internal/generate` (the `generate`/`_COMPLEO_GENERATE_NAME` completion-file-writing flow), `internal/cmdutil` (dependency-free leaf: `CompletionDir`, `WriteCompletionFile`, env var name constants). Each still testable alone.
- Keep code comments short — one line where possible. Explain the non-obvious *why*, not a paragraph of it.
