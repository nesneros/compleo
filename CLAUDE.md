# compleo

A Go tool for zsh scripts. One spec file is the single source of truth for three things:

1. **Parsing** the script's command line
2. **Usage / help message**
3. **zsh completion**

The script calls compleo near the top; compleo parses `"$@"` and prints zsh code that the script `eval`s to set variables. Completion is generated from the same spec, so the three never drift apart.

## Status

Early design phase, but the core pipeline is implemented: `go.mod` at `github.com/nesneros/compleo`, `cmd/compleo/`, `internal/spec`, `internal/parse`, `internal/zsh`, mise tooling, GoReleaser + GitHub Actions CI. Spec parsing, cobra/usage building, and command-line parsing all work end to end; zsh emission (`internal/zsh.Emit`) is still a stub — that's the main remaining gap. Treat anything under "Open questions" as undecided and ask before choosing.

## Design decisions

- **Language:** Go.
- **Target shell:** zsh only. Emit zsh syntax directly; no bash/POSIX compatibility needed. But the design should be open to extension with e.g. bash later.
- **Completion:** built on carapace. The reason is its rich completion actions (hosts, ssh keys, brew formulae, files, ...). Spec fields for completion should stay as close as possible to the carapace-spec format.
- **Macro names:** use the same names as carapace-spec/carapace-bin (e.g. `$files`, `$carapace.tools...`). Do not duplicate the naming knowledge. The macro names are generated by carapace-bin into `pkg/actions/actions_generated.go` (`MacroMap`, `MacroDescriptions`). Import that map and register its entries instead of hand-writing names.
- **Parsing and usage are extensions:** carapace-spec's flags do have `required`/`default` built in, but nothing for flag *types* beyond string/[]string/bool/count, and nothing structured for positionals at all (no name, arity, or type) — compleo's `spec.Command` adds `Positionals` and `FlagTypes` for that.
- **Result delivery:** the Go program prints a zsh script; the calling script `eval`s it. Parsed values go into an associative array (preferred over individual variables).
- **Architecture:** resolved — embed carapace-spec/carapace libraries and build the target spec into an in-memory `cobra.Command` at runtime via `spec.Command`'s `toCarapace().ToCobraE()`. Explicitly NOT carapace's `--codegen`/`Codegen()`: that's an offline one-shot tool that writes static `.go` stub files (with `Run` always a no-op) for hand-finishing carapace-bin's own completers — it assumes a per-command compile step, which doesn't fit compleo (one generic binary, arbitrary spec read fresh every invocation, no compile step per script).
- **Parsing engine:** resolved — cobra/pflag via `ToCobraE()`, not a custom parser. Caveats: this layer only registers real pflag flags for `string`/`[]string`/`bool`/`count` types (defaults, required, mutually-exclusive flags are all enforced for real by cobra) — other flag types must be coerced by compleo from the string value. Positional args get zero parsing/validation from cobra (`Args` is always `cobra.ArbitraryArgs`) — `internal/parse` implements arity/required-ness/binding itself.
- **Spec delivery at runtime:** the target script's spec is read from compleo's stdin, not passed as a file-path argument. This keeps the calling script free to supply the spec as an inline variable, a heredoc, an embedded string, or an external file it cats in itself. Consequence: in pass-through mode compleo's entire argv (after the `parse` token below) is the wrapped script's own arguments — there is no room for compleo's own flags there.
- **compleo's own CLI vs. the pass-through mode:** routing is an explicit `parse` **subcommand**, not a trial-parse-and-fall-through. `run()` (`cmd/compleo/main.go`) checks `args[0] == "parse"` *before* touching compleo's own cobra tree at all; if so, everything after it is the wrapped script's own argv, dispatched to `runPassthrough` (requires `piped`, reads the wrapped spec from stdin). Anything else goes through compleo's own embedded spec (`cmd/compleo/spec.yaml`, loaded via `go:embed`, dogfooding the same format compleo offers to scripts). This was a deliberate fix: the earlier "try compleo's own spec first, fall through on no match" design made `--help`/`--version` ambiguous — virtually every wrapped script has its own `--help`/`--version`, which would've been shadowed by compleo's. `parse` is a fixed token only compleo's own invocation convention ever inserts, so there's no collision.
  - `version`, `validate`, `completion`, `activate` are **subcommands** on compleo's own CLI (`compleo version`, ...), not root flags — deliberately, so they read the same as any other spec subcommand. There's no separate `help` subcommand: only cobra's own `--help`/`-h` flag, available on every (sub)command per the point below. `parse` is also listed as a spec subcommand purely for `compleo --help`'s discoverability — it's never actually dispatched into by cobra, since `run()` intercepts it first.
  - compleo does **not** fight cobra's own automatic `--help` flag, which cobra attaches to every (sub)command by default (root included) with no documented per-command opt-out (confirmed by reading cobra v1.10.2's `execute()`: `InitDefaultHelpFlag()` runs unconditionally before any hook we control, and the help check happens before `PreRun`, so even carapace's own `Standalone()` can't suppress it once `--help` is actually passed). So `compleo validate --help` works too, same as `git commit --help` — this is deliberate, not a bug, and intentionally *not* something compleo tries to restrict to the root command only.
  - `--help` is intercepted internally by cobra before `RunE` runs (for whichever command matched, root or subcommand) — `main.go`'s `helpRequested` recurses the whole command tree checking `Flags().Changed("help")`, since there's no other way to detect it per resolved command. Cobra converts the internal `flag.ErrHelp` to a `nil` error before `cmd.Execute()` returns (in `ExecuteC`), so a genuine `parse.Parse` error and "help was requested" can never both be true — `run()` checks `parseErr` immediately, then `helpRequested` separately, with no ordering dependency between them.
- **Wrapped-script completion install location:** `compleo activate` (`cmd/compleo/main.go`) prints two lines of zsh — `mkdir -p` the completions directory if missing, then `fpath+=(...)` it — meant to be eval'd/sourced in `.zshrc` **before** `compinit` runs (same requirement every `fpath`-based completion installer documents: `compinit`'s directory scan only sees whatever's already on `$fpath` at the moment it runs). The directory itself (`completionDir()`) is `$COMPLEO_COMPLETION_DIR` if set, else `${XDG_DATA_HOME:-~/.local/share}/compleo/completions`. This replaces an earlier idea of having compleo *detect* an existing writable `$fpath` entry (e.g. Homebrew's site-functions) to write into — cleaner for compleo to own a dedicated directory and have the user opt it into `$fpath` once, same pattern as `pyenv`/`direnv`/`zoxide`'s `eval "$(tool init zsh)"`.
  - `activate` also writes compleo's own completion (via `zsh.Completion(ownCmd, ownSpec)`) to `completionDir()/_compleo`, through `writeCompletionFile` — which skips the write entirely when the content is unchanged. This matters because `activate` may run on every shell startup (the `eval "$(tool init zsh)"` pattern), and unconditionally rewriting the file would bump the completions directory's mtime every time, which is exactly what makes `compinit` think it needs to rescan `fpath` instead of trusting `.zcompdump` — so an unconditional rewrite would quietly defeat the whole "many completions stay cheap" argument above. (Confirmed `zsh.Completion`'s output is byte-identical across repeated builds from the same spec, via `TestCompletionIsDeterministic` in `internal/zsh` — load-bearing for this skip-if-unchanged logic to actually skip anything.) Writing a *wrapped script's* generated completion file into this same directory isn't implemented yet; `completionDir()`/`writeCompletionFile` are reusable for whatever does that later.
  - No extra "make this autoload" step is needed beyond the directory being on `$fpath`: `compinit`'s scan only reads each `_*` file's first line (the `#compdef` pragma), caches that scan in `.zcompdump` (invalidated when an `fpath` directory's mtime changes, e.g. a new file appears), and only actually reads/runs a given file's body lazily, on that command's first Tab-press. Carapace's own generated snippet (`zsh.Completion`) — despite ending in top-level executable lines, not just a bare function body — still works correctly dropped as a static autoloaded file for this reason: first Tab-press autoloads it, which defines the real function, serves that first completion, and re-registers `compdef` to point directly at the real function; every later Tab-press skips straight to it.
- **Quoting:** `internal/zsh.Quote` (single-quote style, escaping embedded `'` via `'\''`) is the one tested quoting function CLAUDE.md's Conventions require — used by `activate`'s output today; `zsh.Emit` should use it too once implemented. Its tests include actually `exec.Command("zsh", "-fc", ...)`-round-tripping values with spaces/`$`/backticks/newlines/embedded quotes, not just asserting the Go string shape.
- **internal/spec's API surface:** `ParseYAML` decodes *and* builds the cobra tree (decode + `toCarapace().ToCobraE()` + usage wiring) in one call — it's the one entry point everything uses now. `decodeYAML` (private) is just the raw YAML decode step, used internally. `toCarapace`/`Apply` are also private; nothing outside the package calls them directly anymore.
- **YAML library pin matters:** must use `gopkg.in/yaml.v3`, not `go.yaml.in/yaml/v3` — the pinned `carapace-sh/carapace v1.16.3`'s `command.FlagSet`/`command.Run` have custom `UnmarshalYAML` methods tied to that specific package's `*yaml.Node` type; the other library's decoder silently won't find them (flags parse wrong, with no error). carapace migrates to `go.yaml.in/yaml/v3` after this tag — revisit this pin together.
- **Versioning:** follows carapace-bin's own pattern exactly — `version`/`commit`/`date` vars in `main.go`, populated by GoReleaser's *default* ldflags (no explicit `ldflags:` in `.goreleaser.yml`), with `versionString()` appending `(date) [commit]` only when `version` contains "SNAPSHOT" (GoReleaser's default snapshot template).
- **Canonical carapace org & versions:** the project lives at `carapace-sh` (e.g. `carapace-sh/carapace`, `carapace-sh/carapace-spec`); `rsteube/*` repos now just redirect there and aren't separately maintained. Pin tagged releases: `carapace-spec v1.9.0`, `carapace v1.16.3`, `cobra v1.10.2`, `pflag v1.0.10`.

## Open questions (do not decide silently)

- Whether the spec is a separate YAML file or annotations in the script.
- Name of the associative array (fixed vs chosen by the script).
- Layout for multi-valued results (repeated flags, positional lists): zsh associative arrays hold scalars only, so these need separate arrays or another convention.
- Boolean flag convention in the array (present with a value vs absent).
- Behaviour on `--help` and on bad arguments **in pass-through mode** (`compleo parse ...`): cobra writes help/usage text for the *wrapped script's* cobra tree straight to stdout by default — but stdout there is reserved for the zsh `internal/zsh.Emit` output the wrapped script evals. Not yet fixed; likely needs capturing that output and re-wrapping it as zsh (e.g. `print -- "..."; return 1`) rather than letting it through raw. (This is separate from, and unaffected by, the now-resolved `parse`-routing fix above — compleo's own CLI doesn't have this problem, since its help/errors are the actual intended stdout output.)
- Whether to adopt `replace github.com/spf13/pflag => github.com/carapace-sh/carapace-pflag v1.3.0`. Needed for full flag-syntax support (shorthand-only flags, non-posix single-dash flags, `nargs`-consuming flags) — without it, those flag forms silently fail to register, with no error surfaced. Tradeoff: a dependency on a pflag fork vs. accepting degraded flag-syntax coverage.
- How the wrapped script re-supplies its spec during a live completion callback. `zsh.Completion`'s snippet (carapace's own, via `Gen(cmd).Snippet("zsh")`) re-invokes the binary through `xargs` on every Tab press, with the completion words becoming argv — nothing in that mechanism pipes anything to the child's stdin, so the callback has no way to receive the spec the way normal parsing does (spec read from stdin, per "Spec delivery at runtime" above). Carapace's snippet also suppresses errors (`2>/dev/null`), so this would fail silently, not loudly. Likely needs the wrapped script's own `compdef` wrapper to re-pipe its spec variable instead of using carapace's snippet verbatim — not yet designed.

## Things to verify before relying on them

- The exact name and signature of carapace-spec's macro registration function.
- That current carapace-bin still generates `pkg/actions/actions_generated.go` the way v1.0.2 does.
- Whether carapace-spec's YAML decoder tolerates unknown fields — matters if the same enriched spec file (with compleo's `positionals:`/`flagtypes:` extensions) is ever meant to also be consumable directly by plain carapace-bin/carapace-spec, not just compleo.
- Importing `pkg/actions` links every action package; check the resulting binary size.

## Tooling: mise, not make

Use **mise** for tool versions and tasks. Do not add a Makefile.

- Tool versions (Go, golangci-lint, goreleaser, act) are pinned in `mise.toml` under `[tools]`.
- Simple tasks live in `mise.toml` under `[tasks.*]`; longer scripts are file tasks under `mise-tasks/` (e.g. `mise-tasks/ci-local`) with a `#MISE description=...` header — both run with `mise run <task>`.
- Tasks: `build`, `test`, `lint`, `fmt`, `check` (fmt check, vet, lint, test), `install`, `release-check` (`goreleaser check`, no build), `release-dry-run` (local snapshot build, no publish), `ci-local` (runs `ci.yml` locally via `act`, Docker required).
- If a task you need doesn't exist, add it rather than documenting a raw command here.
- `mise.toml`'s `[env]` sets `COMPLEO_COMPLETION_DIR={{config_root}}/.completions` so `mise x -- go run ./cmd/compleo activate` (or any mise-activated shell) writes into the project instead of the real `~/.local/share/compleo/completions` — convenient for manually inspecting `activate`'s output during development. `.completions/` is gitignored.

## Release & CI

- `.goreleaser.yml`: builds `cmd/compleo` for linux/darwin × amd64/arm64. Relies on GoReleaser's implicit default ldflags (see "Versioning" above) rather than declaring its own.
- `.github/workflows/ci.yml`: `check-ubuntu`/`check-macos` (literal `runs-on`, **not** `strategy: matrix` — see gotcha below) run `mise run check`; `release-check` validates `.goreleaser.yml` on every PR.
- `.github/workflows/release.yml`: runs GoReleaser on `v*` tag pushes.
- `.github/dependabot.yml`: weekly `gomod` + `github-actions` update PRs.
- **act gotchas hard-won while setting up `ci-local`** (all handled in `mise-tasks/ci-local`, don't re-break them):
  - act doesn't read Docker contexts; `DOCKER_HOST` must be set explicitly from `docker context inspect --format '{{.Endpoints.docker.Host}}'` (far more robust than guessing per-tool socket paths — Colima/Rancher Desktop/Docker Desktop all differ, and even Colima's own documented path can be stale across versions).
  - **Confirmed act bug**: `runs-on: ${{ matrix.os }}` under a `strategy.matrix` races when multiple matrix entries evaluate the expression concurrently — they can read each other's resolved platform name (traced to `EvaluateYamlNode` mutating a shared YAML node in act's source). This is *why* `ci.yml` uses two literal jobs instead of a matrix over `os`, not just a style choice.
  - `--container-daemon-socket -` is required to disable bind-mounting the Docker socket into job containers — it fails under any VM-based runtime (Colima, Rancher Desktop) since the host socket path isn't valid inside the VM. None of our jobs need Docker-from-within-a-container anyway.
  - `act push` runs *every* workflow with a `push` trigger, ignoring `release.yml`'s `tags: ["v*"]` filter — `ci-local` scopes to `-W .github/workflows/ci.yml` so it doesn't also attempt (and fail) a real `goreleaser release`.

## Conventions

- Format with `gofmt`; run `go vet` and the configured linter before finishing a change.
- Prefer separate top-level `Test...` functions over table-driven tests, even when it means similar-looking functions repeated — this project's explicit preference, not a Go-wide default.
- Use `testify` (`require`/`assert`) in tests rather than hand-rolled `if err != nil { t.Fatalf }` checks. `require` for preconditions the rest of the test depends on; `assert` for independent checks that should all get reported even if one fails.
- The emitted zsh code is the main contract. Cover it with golden-file tests, and execute the output under `zsh -f` in at least some tests.
- Quoting must be rigorous: arguments can contain spaces, quotes, `$`, backticks, and newlines. Never build emitted shell by naive string concatenation; use one tested quoting function.
- Current package split: `internal/spec` (YAML parsing, types, and building the spec's cobra/completion/usage tree — usage can't be its own package without an import cycle, since it needs `spec.Command`), `internal/parse` (binds a parsed command line to a `Result`), `internal/zsh` (emits the script). Each still testable alone.
- Keep code comments short — one line where possible. Explain the non-obvious *why*, not a paragraph of it.
