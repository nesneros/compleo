# compleo

A Go tool for zsh scripts. One spec file is the single source of truth for three things:

1. **Parsing** the script's command line
2. **Usage / help message**
3. **zsh completion**

The script calls compleo near the top; compleo parses `"$@"` and prints zsh code that the script `eval`s to set variables. Completion is generated from the same spec, so the three never drift apart.

## Status

Early design phase, but the core pipeline is implemented: `go.mod` at `github.com/nesneros/compleo`, `cmd/compleo/`, `internal/spec`, `internal/parse`, `internal/zsh`, mise tooling, GoReleaser + GitHub Actions CI. Spec parsing, cobra/usage building, command-line parsing, zsh emission, and completion generation (both compleo's own and a wrapped script's) all work end to end — see `examples/greet` and `examples/macros`. Treat anything under "Open questions" as undecided and ask before choosing.

## Design decisions

- **Language:** Go.
- **Target shell:** zsh only. Emit zsh syntax directly; no bash/POSIX compatibility needed. Design should stay open to extension with e.g. bash later.
- **Completion:** built on carapace, for its rich completion actions (hosts, ssh keys, brew formulae, files, ...). Spec fields for completion stay as close as possible to the carapace-spec format.
- **Macro names:** use the same names as carapace-spec/carapace-bin (e.g. `$files`, `$carapace.tools...`) — don't duplicate that naming knowledge.
- **Parsing and usage are extensions:** carapace-spec's flags have `required`/`default` but nothing for flag *types* beyond string/[]string/bool/count, and nothing structured for positionals at all. `spec.Command` adds `Positionals` (embeds its own `Type` per item — purely compleo's type, nothing to reuse) and `FlagTypes map[string]Type` (a side-channel map, not a field on each flag: carapace's flag-syntax YAML parsing is unexported with no extension hook, so compleo can't fork a custom `Flag` struct into it).
- **Result delivery:** the Go program prints a zsh script; the calling script `eval`s it. Parsed values go into an associative array.
- **Architecture:** spec is built into an in-memory `cobra.Command` at runtime via `spec.Command`'s private `toCarapace().ToCobraE()`. Not carapace's `--codegen`: that writes static per-command `.go` stubs for an offline compile step, which doesn't fit "one generic binary, arbitrary spec read fresh every invocation."
- **Parsing engine:** cobra/pflag via `ToCobraE()`, not a custom parser. Cobra/pflag only register real flags for `string`/`[]string`/`bool`/`count`; other `flagtypes:`/positional `type:` values are plain strings to them, so `internal/parse`'s `bindFlags`/`bindPositionals` validate those itself via `spec.Type.Validate` — the only place an invalid type declaration is ever caught. Positional arity/required-ness/binding is entirely `internal/parse`'s own (cobra's `Args` is always `cobra.ArbitraryArgs`). A typed flag's `--help` shows its declared type (e.g. `` (`int`) ``) appended to the description by `addFlagTypeHints`, since pflag's `UnquoteUsage` looks for a backtick-quoted segment and uses it as the displayed type instead of `flag.Value.Type()`.
- **Spec delivery at runtime:** the target script's spec is read from compleo's stdin, not a file-path argument — lets the calling script supply it as a heredoc, inline variable, or external file it cats in. Consequence: in `parse` mode, compleo's wrapped-script argv is entirely the wrapped script's own arguments.
- **compleo's own CLI vs. `parse` mode:** `parse` is a real subcommand in `cmd/compleo/spec.yaml`, like `version`/`validate`/`completion`/`activate` — flags: `--name`; positionals: one variadic `args`, absorbing the wrapped script's entire argv. It's dispatched through the exact same generic path as every other compleo subcommand (`parse.Parse(ownCmd, ownSpec, args)`, then `switch result.Path[last]`); `run()`'s `case "parse":` pulls `result.Positionals["args"].Values` and `result.Flags["name"].String` and calls `runEmit` or `runGenerate` depending on `COMPLEO_MODE` (see below). (`--dump`, an earlier debugging flag that tee'd the result to stderr, was removed — no caller left needing it.)
  - `"--"` is optional: it's only needed to disambiguate a wrapped script's own flag from one of compleo's own `parse`-level flags (`--name`, cobra's auto `--help`) — e.g. `compleo parse -- --name` makes `--name` the wrapped script's own. With no collision, `compleo parse world` works with no `--`. This is ordinary pflag behavior (`parseArgs` stops interpreting flags at a bare `--`), not hand-rolled parsing — and it means `compleo parse --help` (before any `--`) shows `parse`'s own flag docs for free.
  - A variadic positional with zero bound values comes back as `nil` (not `[]string{}`) from `bindPositionals`; `parse.Parse` panics on a nil argv. `run()`'s `case "parse":` normalizes `nil` to `[]string{}` before dispatching, since a wrapped script with zero of its own arguments is common, not an edge case.
  - `version`/`validate`/`completion`/`activate` are subcommands on compleo's own CLI, not root flags, so they read the same as any other spec subcommand. There's no separate `help` subcommand, only cobra's own `--help`/`-h`, available on every (sub)command — compleo doesn't fight cobra's automatic `--help` (no documented per-command opt-out exists), so `compleo validate --help` works too, same as `git commit --help`.
  - `--help` is intercepted by cobra before `RunE` runs. `internal/parse`'s `helpRequested` recurses the whole command tree checking `Flags().Changed("help")` and `Parse` sets `Result.HelpRequested` from it right after `cmd.Execute()` succeeds — this can't be inferred from `Path`/`Flags` being empty, because cobra converts `flag.ErrHelp` to a `nil` error before `Execute()` returns, so success alone doesn't say whether the matched command's `RunE` actually ran. A genuine `parse.Parse` error and `HelpRequested` can never both be true.
- **Wrapped-script completion install location:** `compleo activate` prints zsh that `mkdir -p`s the completions directory and does `fpath+=(...)` — meant to run in `.zshrc` **before** `compinit` (`compinit`'s directory scan only sees what's already on `$fpath` when it runs). The directory (`completionDir()`) is `$COMPLEO_COMPLETION_DIR` if set, else `${XDG_DATA_HOME:-~/.local/share}/compleo/completions`.
  - `activate` also writes compleo's own completion to `completionDir()/_compleo` via `writeCompletionFile`, which skips the write when content is unchanged — needed because `activate` may run on every shell startup, and touching the file every time would bump the directory's mtime, which is what makes `compinit` rescan `fpath` instead of trusting its `.zcompdump` cache. This depends on `zsh.Completion`/`Emit` being deterministic for identical input (covered by `TestCompletionIsDeterministic`).
  - No extra "make this autoload" step is needed beyond the directory being on `$fpath`, *if* `compinit` still runs afterward (the documented order): it reads each file's `#compdef` first line at scan time, and only runs the body lazily on that command's first Tab-press. But if `activate` runs in an already-initialized shell (`compinit` already ran once, so adding to `$fpath` alone changes nothing for *this* session), `zsh.EmitActivate` also emits a guarded `autoload -Uz <dir>/* ; (( $+functions[compdef] )) && for f (<dir>/*) compdef ${f:t} ${f:t:s/_//}` — guarded because `compdef` doesn't exist as a command until `compinit` has run once (confirmed empirically), so this must be a no-op in the documented before-`compinit` flow, not an error. `dir` is never empty (`_compleo` is always there), so the glob always matches.
- **Quoting:** `internal/zsh.Quote` (single-quote style, escaping embedded `'` via `'\''`) is the one quoting function used everywhere zsh is emitted.
- **`internal/zsh.Emit`:** a fixed associative array named `compleo` holds every scalar flag's/positional's value (`compleo[name]=value`); a repeatable flag or variadic positional gets its own real zsh array (`compleo_<name>=(...)`) instead, since assoc-array values are scalars only. Booleans are always present as `"true"`/`"false"` (not presence/absence); count flags render as a plain integer string.
  - Assoc-array keys must stay unquoted (bareword) — `compleo['loud']=x` stores the literal key `"'loud'"`, not `"loud"`. Only the value needs `Quote()`; names come from the spec, always simple tokens.
  - A separate array's variable name is sanitized (every non-`[A-Za-z0-9_]` char, e.g. a flag's `-`, becomes `_`), not quoted — a literal hyphen in a zsh variable name breaks even referencing it later (`${my-array[1]}` parses as `${param-default}`, not a subscript). This can collide two differently-sanitized names onto one array; compleo doesn't guard against it — keep spec names distinct.
  - Iteration over `result.Flags`/`result.Positionals` is sorted (`sortedKeys`) for deterministic output, which `activate`'s skip-if-unchanged write depends on.
- **`--help` in `parse` mode:** cobra's `HelpFunc` writes straight to `OutOrStdout()` — the same stream the wrapped script evals as zsh. `runEmit` buffers the wrapped `cmd`'s output (`cmd.SetOut(&helpBuf)`), and if `HelpRequested`, emits `zsh.EmitHelp(helpBuf.String())` instead of `zsh.Emit`. `EmitHelp` wraps the text as `print -r -- <Quote(text)>\nexit 0` — `exit`, not `return`, since `return` inside `eval`'d code only exits an enclosing function if the script wraps its logic in one. `cmd.SilenceErrors`/`SilenceUsage` (set on the wrapped `cmd` too) stop cobra from also writing its own `Error:`/`Usage:` straight to the real stderr alongside compleo's own reported error.
- **Parse errors in `parse` mode are encoded into the output, not returned as a Go error:** `zsh.EmitError(name, err)` formats `"name: err"` itself, prints `print -u2 -- <Quote(...)>\nexit 2`, and returns nil. Exit 2 specifically (not `main()`'s generic exit 1), so a script checking `$?` can tell the two apart. `name` is the spec's `name:` field, not the real `$0` (compleo never sees it — `argv` is literally `"$@"`; `examples/greet` interpolates `${0:t}` into its own `name:` for this). This means a wrapped script needs only `eval "$(compleo parse -- "$@" <<SPEC ... SPEC)"`, no separate `|| exit $?` — eval'ing the output alone stops the script. Gap this doesn't cover: if compleo itself fails to even launch, there's no output to eval at all — an explicit exit-code check is the only way to catch that.
- **`internal/spec`'s API surface:** `ParseYAML` decodes and builds the cobra tree in one call — the one entry point everything uses. `decodeYAML`/`toCarapace`/`Apply` are private.
- **`compleoCmd` panics rather than returning an error on an invalid embedded `spec.yaml`:** it's built in via `go:embed`, so a parse failure there is a bug, not a runtime condition — unlike `runCarapace`/`runParse`, which parse specs genuinely coming from outside and return ordinary errors.
- **YAML library pin matters:** must use `gopkg.in/yaml.v3`, not `go.yaml.in/yaml/v3` — the pinned `carapace-sh/carapace v1.16.3`'s `command.FlagSet`/`command.Run` have custom `UnmarshalYAML` methods tied to that specific package's `*yaml.Node` type; the other library's decoder silently won't find them. Carapace migrates to `go.yaml.in/yaml/v3` after this tag — revisit this pin together.
- **Versioning:** follows carapace-bin's pattern — `version`/`commit`/`date` vars in `cmd/compleo/version.go`, populated by GoReleaser's default ldflags. `versionString()` appends `(date) [commit]` when `version` contains "SNAPSHOT", or when `version` is still `dev` and both `date`/`commit` are set.
- **Canonical carapace org & versions:** the project lives at `carapace-sh`; `rsteube/*` repos just redirect there. Pinned: `carapace-spec v1.9.0`, `carapace v1.16.3`, `cobra v1.10.2`, `pflag v1.0.10`.
- **Generating and serving a wrapped script's own completion:** `COMPLEO_MODE` is an env var `main()` reads once and threads through as a plain `mode string` parameter (not a hidden `os.Getenv` read deeper in the call chain). It changes what the wrapped script's existing, unconditional `eval "$(compleo parse -- "$@" <<SPEC ...)"` line does, with no mode-aware logic needed in the script itself:
  - unset (`""`): parse `"$@"` against the piped spec, as above (`runEmit`).
  - `generate`: build the wrapped script's completion snippet (`zsh.WrappedCompletion`) and write it to `completionDir()/_<name>` (skip-if-unchanged, like `activate`'s own `_compleo`), then report success as self-exiting zsh (`zsh.EmitGenerated`). Triggered by hand: `COMPLEO_MODE=generate ./greet` once, or after a spec change. User-facing (mirrors Click's `_FOO_COMPLETE=zsh_source foo`).
    - `EmitGenerated`'s message is just a one-shot activation hint for the current shell (a new shell picks up the file for free, since `compinit` rescans `$fpath` at startup): `"To activate completion for <name> in this shell, run: autoload -Uz _<name> && compdef _<name> <name>"` — advice for the user to run, not something compleo can do itself (a subprocess can't modify its parent shell's state). Must autoload `_<name>` (the file's own name), not `_<name>_completion` (the function `WrappedCompletion` defines inside it) — autoload resolves by filename, and only `_<name>` matches a real file; calling it is what actually defines and rebinds the inner function. Caught by `TestEmitGeneratedActivationHintActuallyWorksFromColdStart`.
  - There's no `complete` mode (an earlier design had one — superseded, see below). `runParse` only ever branches on `generate` vs. everything else now.
- **Live completion: the spec is embedded in the generated file, not re-fetched by re-running the wrapped script (resolved, was the main design still open earlier):** carapace's own generated snippet always re-invokes `uid.Executable() + " _carapace zsh"` — literally `compleo _carapace zsh <words>`, since `uid.Executable()` returns whatever binary is actually running, not the completed command. compleo reaches that with no spec on stdin at all. The earlier design worked around this by having `WrappedCompletion` patch that invocation to re-run the *wrapped script* instead (`COMPLEO_MODE=complete xargs <name>`), relying on the script's own heredoc to re-deliver its spec. That worked, but required the wrapped script to stay resolvable on `$PATH` forever, for every single Tab press — the root cause of several real "Tab does nothing, silently" bugs hit during development (always `2>/dev/null`-suppressed, so no error either). Superseded by embedding the spec directly:
  - `WrappedCompletion(cmd, name, specFilePath)` leaves carapace's own invocation untouched (so a Tab press dispatches straight to `compleo` itself, same as compleo's own self-completion already does) and instead injects one line right after `function _<name>_completion {`: `local -x COMPLEO_SPEC_FILE=<Quote(specFilePath)>` — function-scoped and exported, so it reaches the `xargs`-spawned `compleo` child but never leaks outside the function (confirmed empirically).
  - **The spec's content lives in a companion file, not the env var itself** (revised from an initial design that embedded the full spec text as `COMPLEO_SPEC=<Quote(specYAML)>`): an env var is subject to OS-level size limits (`ARG_MAX`, shared across argv+envp, commonly ~1–2MB) with no graceful failure if hit; a file has no such practical limit. `runGenerate` writes the raw, already-expanded spec bytes (whatever was actually piped to `compleo parse` at generate time) to `<completionDir>/.<name>.spec.yaml` via the same skip-if-unchanged `writeCompletionFile` the `_<name>` completion file itself uses, then embeds *that path* (not the content) into the generated snippet. The leading dot matters: `EmitActivate`'s `autoload -Uz <dir>/*` globs every file in the completions directory, and zsh's bare `*` glob doesn't match dotfiles by default — without the dot, the companion file would get swept into that autoload loop as a bogus, harmless-but-wrong entry (confirmed empirically, `print -rl -- dir/*` only lists `_greet`, not `.greet.spec.yaml`). Same frozen-at-generate-time tradeoff as before: any shell expansion in the wrapped script's own heredoc (e.g. `${0:t}`, or a `$spec(${0:A:h}/...)` macro's path) has already happened by generate time, so regenerating is needed if the script or its spec changes or moves.
  - On the receiving end, `run()` checks `COMPLEO_SPEC_FILE` *before* building compleo's own `ownCmd` tree, as soon as it sees `args[0] == "_carapace"`: if set, it `os.Open`s the file and passes the `*os.File` straight to `runCarapace` (no need to buffer it into a string first — `spec.ParseYAML` already takes an `io.Reader`), which builds a *fresh* cobra tree from it and dispatches directly into that. If unset (compleo's own completion, or a legacy generated file), falls through to the existing `ownCmd`-based `_carapace` handling, unchanged.
  - **A spec whose own text doesn't declare name: gets it prepended into the companion file** (`runGenerate`): `name: '<name>'\n` + `rawSpec`, making the file a complete, standalone spec — `runCarapace` just parses it with no name param, no filename parsing needed. Keyed off `declaredNamePattern` (`(?m)^name:`, a cheap regex on `rawSpec` itself — column-0-anchored so it doesn't match a subcommand's indented `name:`), not `sp.Name`: `sp.Name` may already be non-empty via `--name` even though `rawSpec`'s own text has no `name:` at all (true of `examples/greet`, which uses `--name="${0:t}"` and no `name:` field) — checking `sp.Name` instead was tried and found to miss exactly this case. A regex avoids the cost of a second full `spec.ParseYAML` just to tell them apart.
  - This also means the raw wire format carapace's `_carapace` writes needs no wrapping anymore: it goes straight into the generated completion function's own `lines="$(...)"` capture, the same way it already does for compleo's self-completion — there's no wrapped script in the loop anymore for a Tab press to accidentally `eval`. `EmitComplete`/`runComplete`/`modeComplete` are gone; nothing else used them.
  - Net effect: a wrapped script doesn't need `$PATH` at all for *using* its completion (every Tab press) — only, at most, for `compleo generate` itself. `mise.toml`'s `_.path` (adding `examples/` to `$PATH`) still matters for *generating* the demo scripts' completions, just no longer for using them afterward.
  - `compleo generate <script>` is a thin convenience subcommand (`runGenerateFor`): resolves `script` via `exec.LookPath`, then runs it as a subprocess with `COMPLEO_MODE=generate` set — exactly equivalent to typing `COMPLEO_MODE=generate <script>` by hand. Its `script` positional (renamed from `name`, which was confusing once a path became valid too) completes via `$compleo.scripts` (below), not carapace's generic `$executables`. Before executing, it checks `spec.IsCompleoScript(path)` (same check `$compleo.scripts` uses) and refuses otherwise — a basic sanity check, not a security boundary, since it only ever runs *something already found on `$PATH`*.
  - **`$PATH` isn't strictly required even for `generate`**: `script` can be a path (`compleo generate ./examples/greet`, or an absolute path) instead of a bare name — `exec.LookPath` resolves a path containing `/` directly, without consulting `$PATH` at all (confirmed in Go's source/docs). `COMPLEO_GENERATE_NAME` is set from `filepath.Base(script)`, not `script` itself — it must be a bare name to match what the script's own `${0:t}` (or a hardcoded `name:`) computes; passing the whole path through unchanged used to make every such invocation fail with a spurious "spec declares name: ..., but ./examples/greet was invoked" mismatch (confirmed, then fixed).
  - **`name:` in the spec is now optional** (resolved): `runGenerateFor` passes the resolved name through as `COMPLEO_GENERATE_NAME`, and `runGenerate` uses it to fill in a missing `name:` — the common case for a wrapped script's own heredoc spec, since there's nothing to conflict with. If `name:` *is* declared and disagrees with the invoked name, `runGenerate` fails outright (an error, not a silent override as an earlier design did) — generating under the wrong name would otherwise silently break Tab-completion for what's actually typed. This check only applies to the `generate <script>` path; `COMPLEO_MODE=generate ./script` run by hand (no `COMPLEO_GENERATE_NAME`) still just uses `sp.Name` as-is, with no such authority to check against.
  - Without a `name:` at all, `--help` still has to render *something*: `ParseYAML` sets `cmd.Use = "<script>"` when `sp.Name == ""`, right before `applySpec`/`wire` build the synopsis from it — otherwise cobra's `Name()` reads the empty `Use` as a blank first word, showing up as a stray extra space before `[flags]` in the printed "Usage:" line (and "help for this command" instead of naming anything). `<script>` is a placeholder, not a guess — compleo has no way to know the real invoked name here (no `COMPLEO_GENERATE_NAME` authority outside the `generate` path, and compleo never sees `$0` either way).
  - **`compleo parse --name`** (typically `--name "${0:t}"`) lets a spec's heredoc drop `name:` and quote its delimiter (`<<'SPEC'`, no `$`/`` ` `` escaping anywhere in the body). `spec.ParseYAML(r, name)` takes the name directly: fills in a missing `name:`, errors on a mismatch with a declared one, before building `cmd` — so `cmd.Use`/`cmd.Name()` are already correct, no post-hoc rename needed. `runParse` just passes `--name`'s value through; every other caller passes `""`.
  - **`compleo up` — a subcommand that writes the `compleo parse --name=... -- "$@"` invocation for you**, so a script doesn't need to write `--name`/`--`/`"$@"` at all: `eval "$(compleo up <<SPEC ... SPEC)"` is the whole line. `runUp` (`cmd/compleo/main.go`) just reads the piped spec and calls `zsh.EmitUp`, which prints `` eval "$(compleo parse --name="${0:t}" -- "$@" <<<%s)" `` with the spec embedded via `Quote()` as a `<<<` here-string (not a heredoc — no delimiter to pick, so no collision risk with spec content; `Quote()` already handles arbitrary content, confirmed with embedded `'`/`$`/`` ` ``). This means the `eval` the script runs expands into a *second* `eval "$(compleo parse ...)"`, invoking compleo again as a fresh subprocess — deliberate, not an oversight: `up` genuinely cannot know the calling script's own `$0`/`"$@"` itself (same reason `compleo` never sees them anywhere else), so the only way to fill them in is to emit code that references them directly in the *script's own* shell context, which requires a second, nested invocation.
    - `up` doesn't branch on `COMPLEO_MODE` at all — confirmed empirically that `COMPLEO_MODE=generate` set on the wrapped script's own invocation still reaches the *inner* `compleo parse` call unchanged (plain env var inheritance across the nested `eval`/subprocess), so `generate` mode and normal parsing both work through `up` with zero mode-awareness needed in `EmitUp` itself.
    - `up` has no flags of its own — there's nowhere to attach one, since its only job is to transform stdin into the re-invocation text. `compleo parse --name="${0:t}" -- "$@"` directly is still there for anyone who needs finer control over the invocation itself.
    - An external spec file no longer needs a hardcoded `name:` either, now that `up` always supplies one: `eval "$(compleo up < "${0:A:h}/greet.spec.yaml")"` works with a nameless file (confirmed) — the earlier "name: has to be hardcoded for a file" caveat only applied to the plain `parse` form.
    - **A spec needing genuinely dynamic content** has two options, chosen by how much of the spec needs it. `examples/other_spec`'s `$spec(...)` macro needs one absolute path only the running script can compute (`${0:A:h}`) — with just that one thing dynamic, it keeps the heredoc unquoted (`<<SPEC`, not `<<'SPEC'`) straight into `up`, escaping the handful of literal `\$spec` mentions (same tradeoff `examples/greet`/`examples/macros` make the other way, just cheaper here since there's only one macro to escape). When *most* of the spec is static and only a small dynamic piece doesn't fit a quoted heredoc at all, capture the heredoc into a variable instead (`spec=$(<<'SPEC' ... SPEC)` — no `cat` needed, zsh reads a heredoc straight into a command substitution on its own, confirmed) and splice the dynamic piece in afterward via a plain zsh substitution (e.g. `${spec//@PLACEHOLDER@/${0:A:h}}`) before piping to `up` via `<<<`.
- **`$compleo.scripts` — compleo's first custom macro:** `internal/spec/macros.go` registers it via carapace-spec's `AddMacro`/`MacroN`. Narrower than `$executables` for `compleo generate <TAB>`: only offers executables on `$PATH` that look like they wrap compleo (shebang present, plus the literal word "compleo" in the first 4KB — `IsCompleoScript`, checked natively in Go, no `file` subprocess per candidate).
  - `actionScripts()` merges that filtered `$PATH` list with carapace's own `ActionFiles()` (`carapace.Batch(...).ToA()`), since `script` can be a path too (see above) — path candidates are unfiltered (carapace's path completion has no hook to hand it a content-based predicate), same tradeoff the `$files` macro already has.
  - `AddMacro("scripts", ...)` registers under the internal key `_.scripts`; `action.go`'s `ActionMacro` rewrites `$<running-binary-name>.foo` to `$_.foo` before lookup — so `$compleo.scripts` only dispatches when compleo is the running binary (true for every real invocation; tests use `$_.scripts` directly instead). Same mechanism carapace-bin uses for `$carapace.*`, not compleo-specific.
  - Macro registration is global, so any wrapped script's own spec can use `$compleo.scripts` too.

## Open questions (do not decide silently)

- Whether the spec is a separate YAML file or annotations in the script.
- Whether to adopt `replace github.com/spf13/pflag => github.com/carapace-sh/carapace-pflag v1.3.0`, needed for full flag-syntax support (shorthand-only flags, non-posix single-dash flags, `nargs`-consuming flags) — without it those forms silently fail to register. Tradeoff: a pflag-fork dependency vs. degraded flag-syntax coverage.
- Nothing yet orchestrates running `COMPLEO_MODE=generate` across every wrapped script a user has — today it's a manual, per-script step. Whether `activate` (or something else) should ever discover and regenerate wrapped scripts' completions in bulk is undecided.
- `Type` (`flagtypes:`/positional `type:`) is currently a plain enum with no attributes — e.g. `path` has no way to require the value already exist, or be specifically a file vs. a directory. General validation attributes for flags (and positionals) were floated — e.g. a shorthand-or-object shape, `times: int` staying as today's bare string but `outdir: {type: path, exists: true, must: directory}` when there's something to configure (mirroring how carapace-spec's own flags already accept a string shorthand or a full object). Open: whether this stays scoped to path existence/kind, or becomes a general attribute mechanism (e.g. int min/max, string pattern) — deliberately deferred, not decided.

## Tooling: mise, not make

Use **mise** for tool versions and tasks. Do not add a Makefile.

- Tool versions (Go, golangci-lint, goreleaser, act) are pinned in `mise.toml` under `[tools]`.
- Simple tasks live in `mise.toml` under `[tasks.*]`; longer scripts are file tasks under `mise-tasks/` (e.g. `mise-tasks/ci-local`) with a `#MISE description=...` header — both run with `mise run <task>`.
- Tasks: `build`, `test`, `lint`, `fmt`, `check` (fmt check, vet, lint, test), `install`, `release-check` (`goreleaser check`, no build), `release-dry-run` (local snapshot build, no publish), `ci-local` (runs `ci.yml` locally via `act`, Docker required).
- If a task you need doesn't exist, add it rather than documenting a raw command here.
- `mise.toml`'s `[env]`: `COMPLEO_COMPLETION_DIR={{config_root}}/.completions` so a mise-activated shell (or `mise x -- ...`) writes into the project instead of the real `~/.local/share/compleo/completions` (`.completions/` is gitignored). `_.path = ["{{config_root}}/examples"]` puts the demo scripts (`greet`, `macros`) on `$PATH` by bare name, since their generated completions need that to work at all (see "Generating and serving a wrapped script's own completion" above).

## Release & CI

- `.goreleaser.yml`: builds `cmd/compleo` for linux/darwin × amd64/arm64. Relies on GoReleaser's implicit default ldflags (see "Versioning" above) rather than declaring its own.
- `.github/workflows/ci.yml`: `check-ubuntu`/`check-macos` (literal `runs-on`, **not** `strategy: matrix` — see below) run `mise run check`; `release-check` validates `.goreleaser.yml` on every PR.
- `.github/workflows/release.yml`: runs GoReleaser on `v*` tag pushes.
- `.github/dependabot.yml`: weekly `gomod` + `github-actions` update PRs.
- **act gotchas** (all handled in `mise-tasks/ci-local`, don't re-break them):
  - act doesn't read Docker contexts; `DOCKER_HOST` must be set explicitly from `docker context inspect --format '{{.Endpoints.docker.Host}}'`.
  - `runs-on: ${{ matrix.os }}` under a `strategy.matrix` races in act when multiple matrix entries evaluate the expression concurrently (a shared-YAML-node mutation bug in act's `EvaluateYamlNode`) — why `ci.yml` uses two literal jobs instead of a matrix over `os`.
  - `--container-daemon-socket -` disables bind-mounting the Docker socket into job containers — required under any VM-based runtime (Colima, Rancher Desktop), where the host socket path isn't valid inside the VM.
  - `act push` runs every workflow with a `push` trigger, ignoring `release.yml`'s `tags: ["v*"]` filter — `ci-local` scopes to `-W .github/workflows/ci.yml` so it doesn't also attempt a real `goreleaser release`.

## Conventions

- Format with `gofmt`; run `go vet` and the configured linter before finishing a change.
- Prefer separate top-level `Test...` functions over table-driven tests, even when it means similar-looking functions repeated — this project's explicit preference, not a Go-wide default.
- Use `testify` (`require`/`assert`) in tests rather than hand-rolled `if err != nil { t.Fatalf }` checks. `require` for preconditions the rest of the test depends on; `assert` for independent checks that should all get reported even if one fails.
- The emitted zsh code is the main contract. Cover it with golden-file tests, and execute the output under `zsh -f` in at least some tests.
- Quoting must be rigorous: arguments can contain spaces, quotes, `$`, backticks, and newlines. Never build emitted shell by naive string concatenation; use one tested quoting function.
- Current package split: `internal/spec` (YAML parsing, types, and building the spec's cobra/completion/usage tree — usage can't be its own package without an import cycle, since it needs `spec.Command`), `internal/parse` (binds a parsed command line to a `Result`), `internal/zsh` (emits the script). Each still testable alone.
- Keep code comments short — one line where possible. Explain the non-obvious *why*, not a paragraph of it.
