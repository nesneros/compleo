# compleo

A Go tool for zsh scripts. One spec file is the single source of truth for three things:

1. **Parsing** the script's command line
2. **Usage / help message**
3. **zsh completion**

The script calls compleo near the top; compleo parses `"$@"` and prints zsh code that the script `eval`s to set variables. Completion is generated from the same spec, so the three never drift apart.

## Status

Early design phase, but the core pipeline is implemented: `go.mod` at `github.com/nesneros/compleo`, `cmd/compleo/`, `internal/spec`, `internal/parse`, `internal/zsh`, mise tooling, GoReleaser + GitHub Actions CI. Spec parsing, cobra/usage building, command-line parsing, and zsh emission (`internal/zsh.Emit`) all work end to end — see `examples/greet` for a real wrapped script exercising the whole thing. Treat anything under "Open questions" as undecided and ask before choosing.

## Design decisions

- **Language:** Go.
- **Target shell:** zsh only. Emit zsh syntax directly; no bash/POSIX compatibility needed. But the design should be open to extension with e.g. bash later.
- **Completion:** built on carapace. The reason is its rich completion actions (hosts, ssh keys, brew formulae, files, ...). Spec fields for completion should stay as close as possible to the carapace-spec format.
- **Macro names:** use the same names as carapace-spec/carapace-bin (e.g. `$files`, `$carapace.tools...`). Do not duplicate the naming knowledge. The macro names are generated by carapace-bin into `pkg/actions/actions_generated.go` (`MacroMap`, `MacroDescriptions`). Import that map and register its entries instead of hand-writing names.
- **Parsing and usage are extensions:** carapace-spec's flags do have `required`/`default` built in, but nothing for flag *types* beyond string/[]string/bool/count, and nothing structured for positionals at all (no name, arity, or type) — compleo's `spec.Command` adds `Positionals` and `FlagTypes` for that.
  - **Why `Positionals` embeds its `Type` per-item but `FlagTypes` is a separate side-channel map, not a field on each flag:** `Positional` is entirely compleo's own type (carapace-spec has no positional concept at all to reuse), so there's nothing stopping `Type` living directly on it. Flags are different: carapace's `command.Flag`/`FlagSet` YAML decoding (the `-c, --count=`/`--tag*=` shorthand-and-modifier syntax) is handled by `FlagSet.UnmarshalYAML`, which calls carapace's own `parseFlag` — unexported, along with its `findNamedMatches` helper (confirmed in `pkg/command/flag.go`; the package's only exported `Flag`/`FlagSet` surface is `Name()`, `MarshalYAML`, `UnmarshalYAML`). So compleo can't define its own `Flag` struct (embedding `command.Flag` plus a `Type` field, the way `spec.Command` embeds `command.Command`) and still reuse carapace's flag-syntax parser — there's no hook to extend it, only to reimplement it. `FlagTypes map[string]Type` is the only way to attach type metadata to a flag without forking that parser, which would violate the macro-naming principle just above (don't duplicate carapace-spec's own knowledge).
- **Result delivery:** the Go program prints a zsh script; the calling script `eval`s it. Parsed values go into an associative array (preferred over individual variables).
- **Architecture:** resolved — embed carapace-spec/carapace libraries and build the target spec into an in-memory `cobra.Command` at runtime via `spec.Command`'s `toCarapace().ToCobraE()`. Explicitly NOT carapace's `--codegen`/`Codegen()`: that's an offline one-shot tool that writes static `.go` stub files (with `Run` always a no-op) for hand-finishing carapace-bin's own completers — it assumes a per-command compile step, which doesn't fit compleo (one generic binary, arbitrary spec read fresh every invocation, no compile step per script).
- **Parsing engine:** resolved — cobra/pflag via `ToCobraE()`, not a custom parser. Caveats: this layer only registers real pflag flags for `string`/`[]string`/`bool`/`count` types (defaults, required, mutually-exclusive flags are all enforced for real by cobra) — other flag types are plain strings to cobra/pflag, so compleo validates them itself via `spec.Type.Validate` (called from `internal/parse`'s `bindFlags`/`bindPositionals`, using `sp.FlagTypes`/`Positional.Type`) — this is the only place an invalid `flagtypes:`/positional `type:` value is ever caught; until this existed, declaring e.g. `flagtypes: times: int` was silently decorative. Positional args get zero parsing/validation from cobra (`Args` is always `cobra.ArbitraryArgs`) — `internal/parse` implements arity/required-ness/binding itself.
  - A typed flag's `--help` output used to show pflag's actual registered type (`--times string`, not `--times int`) since compleo types aren't real pflag types. Fixed in `toCarapace()`/`addFlagTypeHints`: appends `` (`int`) `` etc. to the flag's description for any `flagtypes:`-declared, non-string type. This works because pflag's `UnquoteUsage` (confirmed in source) looks for a backtick-quoted segment in the usage string and uses it as the displayed type name *instead of* `flag.Value.Type()` — but it only *strips the backticks*, the quoted text itself stays visible in the description, so the hint has to read naturally as trailing prose; a bare `` `int` `` with no parens renders as an awkward dangling word (verified both ways before picking the parenthesized form).
- **Spec delivery at runtime:** the target script's spec is read from compleo's stdin, not passed as a file-path argument. This keeps the calling script free to supply the spec as an inline variable, a heredoc, an embedded string, or an external file it cats in itself. Consequence: in pass-through mode compleo's entire argv (after the `parse` token below) is the wrapped script's own arguments — there is no room for compleo's own flags there.
- **compleo's own CLI vs. the pass-through mode:** `parse` is a real subcommand in `cmd/compleo/spec.yaml`, like `version`/`validate`/`completion`/`activate` — flags: `--dump` (print the result to stderr too, for debugging); positionals: one variadic `args`, absorbing the wrapped script's entire argv. It's dispatched through the exact same generic path as every other compleo subcommand (`parse.Parse(ownCmd, ownSpec, args)`, then `switch result.Path[last]`) — no early interception of `args[0] == "parse"` before touching compleo's own cobra tree; that approach (and an even earlier "try compleo's own spec first, fall through on no match" design, which made `--help`/`--version` ambiguous against the wrapped script's own) have both been superseded. A `case "parse":` in `run()`'s switch pulls `result.Positionals["args"].Values` and `result.Flags["dump"].Bool` out and calls `runParse` (renamed from `runPassthrough`, since there's no longer a separate dispatch function competing for that name).
  - **`"--" is optional, not mandatory** (a deliberate relaxation from an earlier, stricter design): it's only needed to disambiguate a wrapped script's own flag from one of compleo's own `parse`-level flags (`--dump`, cobra's auto `--help`) — e.g. `compleo parse -- --dump` makes `--dump` the wrapped script's own, not compleo's. With no collision, `compleo parse world` works fine with no `--` at all. This isn't hand-rolled string-scanning: it's ordinary cobra/pflag flag parsing on the `parse` subcommand's own registered flags, and pflag's own `parseArgs` (confirmed in source) already stops interpreting anything as a flag the moment it sees a bare `--`. One consequence worth knowing: this also means `compleo parse --help` (before any `--`) shows help for `parse`'s own flags, for free, with no extra code.
  - **Gotcha this surfaced:** a variadic positional with zero bound values comes back as `nil` (not an empty slice) from `bindPositionals`'s `append([]string(nil), rest...)` with an empty `rest` — and `parse.Parse` panics on a nil argv. `run()`'s `case "parse":` explicitly normalizes `nil` to `[]string{}` before calling `runParse`, since a wrapped script with zero of its own arguments (e.g. `compleo parse` alone) is a real, common case, not an edge case to ignore.
  - `version`, `validate`, `completion`, `activate` are **subcommands** on compleo's own CLI (`compleo version`, ...), not root flags — deliberately, so they read the same as any other spec subcommand. There's no separate `help` subcommand: only cobra's own `--help`/`-h` flag, available on every (sub)command per the point below. `parse` is also listed as a spec subcommand purely for `compleo --help`'s discoverability — it's never actually dispatched into by cobra, since `run()` intercepts it first.
  - compleo does **not** fight cobra's own automatic `--help` flag, which cobra attaches to every (sub)command by default (root included) with no documented per-command opt-out (confirmed by reading cobra v1.10.2's `execute()`: `InitDefaultHelpFlag()` runs unconditionally before any hook we control, and the help check happens before `PreRun`, so even carapace's own `Standalone()` can't suppress it once `--help` is actually passed). So `compleo validate --help` works too, same as `git commit --help` — this is deliberate, not a bug, and intentionally *not* something compleo tries to restrict to the root command only.
  - `--help` is intercepted internally by cobra before `RunE` runs (for whichever command matched, root or subcommand) — `internal/parse`'s private `helpRequested` recurses the whole command tree checking `Flags().Changed("help")`, since there's no other way to detect it per resolved command, and `Parse` sets `Result.HelpRequested` from it right after `cmd.Execute()` succeeds. This has to live in `Result`, not be inferred from `Path`/`Flags` being empty: cobra converts the internal `flag.ErrHelp` to a `nil` error before `cmd.Execute()` returns (in `ExecuteC`), so `Execute()` succeeding tells you nothing about whether the matched command's own `RunE` (the thing that populates `Path`/`Flags`/`Positionals`) actually ran — it never does when help was shown, on *any* matched command, not just root. A genuine `parse.Parse` error and `HelpRequested` can never both be true, confirmed the same way — `run()` checks `parseErr` immediately, then `result.HelpRequested` separately, with no ordering dependency between them.
- **Wrapped-script completion install location:** `compleo activate` (`cmd/compleo/main.go`) prints two lines of zsh — `mkdir -p` the completions directory if missing, then `fpath+=(...)` it — meant to be eval'd/sourced in `.zshrc` **before** `compinit` runs (same requirement every `fpath`-based completion installer documents: `compinit`'s directory scan only sees whatever's already on `$fpath` at the moment it runs). The directory itself (`completionDir()`) is `$COMPLEO_COMPLETION_DIR` if set, else `${XDG_DATA_HOME:-~/.local/share}/compleo/completions`. This replaces an earlier idea of having compleo *detect* an existing writable `$fpath` entry (e.g. Homebrew's site-functions) to write into — cleaner for compleo to own a dedicated directory and have the user opt it into `$fpath` once, same pattern as `pyenv`/`direnv`/`zoxide`'s `eval "$(tool init zsh)"`.
  - `activate` also writes compleo's own completion (via `zsh.Completion(ownCmd)`) to `completionDir()/_compleo`, through `writeCompletionFile` — which skips the write entirely when the content is unchanged. This matters because `activate` may run on every shell startup (the `eval "$(tool init zsh)"` pattern), and unconditionally rewriting the file would bump the completions directory's mtime every time, which is exactly what makes `compinit` think it needs to rescan `fpath` instead of trusting `.zcompdump` — so an unconditional rewrite would quietly defeat the whole "many completions stay cheap" argument above. (Confirmed `zsh.Completion`'s output is byte-identical across repeated builds from the same spec, via `TestCompletionIsDeterministic` in `internal/zsh` — load-bearing for this skip-if-unchanged logic to actually skip anything.) Writing a *wrapped script's* generated completion file into this same directory isn't implemented yet; `completionDir()`/`writeCompletionFile` are reusable for whatever does that later.
  - No extra "make this autoload" step is needed beyond the directory being on `$fpath`: `compinit`'s scan only reads each `_*` file's first line (the `#compdef` pragma), caches that scan in `.zcompdump` (invalidated when an `fpath` directory's mtime changes, e.g. a new file appears), and only actually reads/runs a given file's body lazily, on that command's first Tab-press. Carapace's own generated snippet (`zsh.Completion`) — despite ending in top-level executable lines, not just a bare function body — still works correctly dropped as a static autoloaded file for this reason: first Tab-press autoloads it, which defines the real function, serves that first completion, and re-registers `compdef` to point directly at the real function; every later Tab-press skips straight to it.
- **Quoting:** `internal/zsh.Quote` (single-quote style, escaping embedded `'` via `'\''`) is the one tested quoting function CLAUDE.md's Conventions require — used by both `activate`'s and `Emit`'s output. Its tests include actually `exec.Command("zsh", "-fc", ...)`-round-tripping values with spaces/`$`/backticks/newlines/embedded quotes, not just asserting the Go string shape.
- **`internal/zsh.Emit` (resolved, was the main remaining gap):** a fixed associative array named `compleo` holds every scalar flag's and positional's value — a non-repeatable flag or non-variadic positional as `compleo[name]=value`; a repeatable flag or variadic positional instead gets its own dedicated real zsh array (`compleo_<name>=(...)`), since zsh assoc-array values are scalars only. Booleans are always present as the string `"true"`/`"false"` (not presence/absence), so every flag kind reads the same way. Count flags render as a plain integer string. All three were explicit "do not decide silently" calls the user made (recorded here so they're not re-litigated).
  - **Assoc-array keys must stay unquoted (bareword)** — `compleo['loud']=x` does **not** store key `"loud"`, it stores the literal key `"'loud'"`, confirmed empirically (`typeset -p compleo` showed `[\''loud'\']=...`). Zsh assoc-array subscripts don't get the quote-removal normal shell words get. Only the *value* side needs `Quote()`; flag/positional names come from the spec, not end-user input, and are always simple tokens, so leaving them unquoted is safe.
  - **A separate array's variable name is sanitized**, not quoted: `compleo_<name>` replaces every non-`[A-Za-z0-9_]` character (e.g. the `-` in `dry-run`) with `_`, since a literal hyphen in a zsh variable name breaks even *referencing* it later — `${my-array[1]}` parses as the `${param-default}` operator, not a subscript on a variable named `my-array` (also confirmed empirically). This can collide two differently-named flags/positionals onto the same sanitized array name, and a flag and a positional sharing one name collide in the main `compleo` array too — compleo doesn't currently guard against either; keep spec names distinct.
  - Iteration order over `result.Flags`/`result.Positionals` (plain Go maps) is sorted via a generic `sortedKeys[K cmp.Ordered, V any](m map[K]V) []K` (`slices.Sorted(maps.Keys(m))`, Go 1.23+ stdlib) for deterministic output — this also matters for `activate`'s write-only-if-changed logic (see below), which depends on `zsh.Completion`/`Emit` producing byte-identical output for identical input.
- **`--help` in pass-through mode (resolved):** cobra's default `HelpFunc` writes straight to `OutOrStdout()` (confirmed in source, with cobra's own comment citing spf13/cobra#1002) — the same stdout the wrapped script evals as zsh. `runParse` now buffers the wrapped `cmd`'s output (`cmd.SetOut(&helpBuf)`) before calling `parse.Parse`, then checks `helpRequested(cmd)` (same helper used for compleo's own CLI) and, if true, emits `zsh.EmitHelp(helpBuf.String())` instead of `zsh.Emit`. `EmitHelp` wraps the captured text as `print -r -- <Quote(text)>\nexit 0` — `exit`, not `return`: confirmed empirically that `return` inside `eval`'d code only exits the *enclosing function* if the wrapped script wraps its logic in one (e.g. `function main { ...; }; main "$@"`), leaving the outer script to keep running after `--help`; `exit` always stops the whole process regardless of nesting. The non-help error path (`unknown flag`, missing required positional, ...) never corrupted stdout — confirmed via source that cobra's error/usage reporting goes through `OutOrStderr()`/`ErrOrStderr()` (not `OutOrStdout()`), both defaulting to `os.Stderr`, a separate field from the one `SetOut` touches — but it did duplicate the error message: cobra's own `Error: ...` (and `Usage:` block, unless silenced) landed on the real `os.Stderr` right alongside `main()`'s own reported error. Fixed by also setting `cmd.SilenceErrors = true` / `cmd.SilenceUsage = true` on the wrapped `cmd`, same as `compleoCmd()` already does for compleo's own CLI.
- **Parse errors in pass-through mode are encoded into the output, not returned as a Go error** (`zsh.EmitError(name string, err error)`, parallel to `zsh.EmitHelp`): `runParse` calls `zsh.EmitError(sp.Name, err)`, which formats `"name: err"` itself (callers don't pre-format), prints `print -u2 -- <Quote("name: err")>\nexit 2` to `out`, and returns nil. Exit **2** specifically, not main()'s generic exit(1) for compleo's own invocation failures — the conventional Unix "bad usage" code, so a script checking `$?` can tell the two apart. `name` is the spec's declared `name:`, not the real invoked script path/`$0` (compleo has no visibility into that at all: `argv` passed to `parse.Parse` is literally `"$@"`, which by shell convention never includes `$0`; `examples/greet` works around this itself by interpolating `${0:t}` into its own `name:` field before piping the spec). This means a wrapped script only needs `eval "$(compleo parse -- "$@" <<SPEC ... SPEC)"` — no separate `|| exit $?` — since eval'ing the output alone stops the script on a bad arg (verified: `TestRunParseErrorOutputStopsScriptWhenEvaldUnderRealZsh` execs a real zsh with an unreachable statement after the eval, confirming both the exit code and that it doesn't run). The remaining gap this doesn't cover: if compleo itself fails to even launch (binary missing, not executable, ...), there's no output to eval at all — an explicit exit-code check is still the only way to catch *that*, not something `EmitError` can help with since compleo never ran.
- **internal/spec's API surface:** `ParseYAML` decodes *and* builds the cobra tree (decode + `toCarapace().ToCobraE()` + usage wiring) in one call — it's the one entry point everything uses now. `decodeYAML` (private) is just the raw YAML decode step, used internally. `toCarapace`/`Apply` are also private; nothing outside the package calls them directly anymore.
- **YAML library pin matters:** must use `gopkg.in/yaml.v3`, not `go.yaml.in/yaml/v3` — the pinned `carapace-sh/carapace v1.16.3`'s `command.FlagSet`/`command.Run` have custom `UnmarshalYAML` methods tied to that specific package's `*yaml.Node` type; the other library's decoder silently won't find them (flags parse wrong, with no error). carapace migrates to `go.yaml.in/yaml/v3` after this tag — revisit this pin together.
- **Versioning:** follows carapace-bin's own pattern exactly — `version`/`commit`/`date` vars in `cmd/compleo/version.go`, populated by GoReleaser's *default* ldflags (no explicit `ldflags:` in `.goreleaser.yml`), with `versionString()` appending `(date) [commit]` when `version` contains "SNAPSHOT" (GoReleaser's default snapshot template), and also when `version` is still the default `dev` and both `date` and `commit` were set.
- **Canonical carapace org & versions:** the project lives at `carapace-sh` (e.g. `carapace-sh/carapace`, `carapace-sh/carapace-spec`); `rsteube/*` repos now just redirect there and aren't separately maintained. Pin tagged releases: `carapace-spec v1.9.0`, `carapace v1.16.3`, `cobra v1.10.2`, `pflag v1.0.10`.
- **Generating and serving a wrapped script's own completion (resolved; was the open question about live-callback spec re-delivery):** `COMPLEO_MODE` is an env var compleo's own `main()` reads once and threads through as a plain parameter (`run`/`runParse`'s `mode string`, not a hidden `os.Getenv` read deeper in the call chain — consistent with how `piped` is already precomputed and passed in for testability). It changes what the wrapped script's existing, unconditional `eval "$(compleo parse -- "$@" <<SPEC ...)"` line does, without the script itself needing any mode-aware logic:
  - unset (`""`): today's behavior — parse `"$@"` against the piped spec.
  - `generate`: build the wrapped script's own completion snippet (`zsh.WrappedCompletion`) and write it to `completionDir()/_<name>` (`writeCompletionFile`, same skip-if-unchanged directory `activate` uses for `_compleo`), then report success as self-exiting zsh (`zsh.EmitGenerated`, same `print -u2 -- ...; exit 0` convention as `EmitHelp`/`EmitError`). Triggered by hand: `COMPLEO_MODE=generate ./greet` once (or after a spec change) to (re)install `_greet`.
  - `complete`: serve one live Tab-press completion request, using the exact same piped spec a normal run would get.
  - Why one env var solves both the generation trigger *and* the previously-unsolved live-callback spec-delivery problem: carapace's own generated snippet (confirmed from `carapace@v1.16.3/internal/shell/zsh/snippet.go`) always re-invokes `uid.Executable() + " _carapace zsh"` on every Tab press — i.e. literally `compleo _carapace zsh <words>` for *any* spec, since `uid.Executable()` returns whatever binary is actually running, not the completed command's name. For a wrapped script that's useless: that re-invocation reaches compleo with no spec on stdin at all (`_carapace`'s `xargs` re-invocation has no stdin-piping mechanism — the exact gap this open question used to describe). The fix is to never let the Tab-press re-invoke compleo directly. `zsh.WrappedCompletion(cmd)` takes carapace's own generated snippet (via the existing `Completion(cmd)`) and replaces just the one substring that differs — `"xargs " + uid.Executable() + " _carapace zsh"` becomes `"COMPLEO_MODE=complete xargs " + cmd.Name()` — leaving every other line (the quote-retry dance, `CARAPACE_COMPLINE`/`CARAPACE_ZSH_HASH_DIRS`, candidate formatting) exactly as carapace generated it. So the generated `_greet` file's Tab-press callback re-invokes `greet` itself, not compleo — and `greet`'s own top-of-script `eval` line runs again exactly as it does for a normal invocation, re-delivering the spec via its heredoc, just with `COMPLEO_MODE=complete` now set. No second spec-delivery mechanism was needed; the existing one just gets exercised a second way.
  - `WrappedCompletion` computes its own expected `oldInvocation` substring by calling `uid.Executable()` itself (same package carapace uses) rather than hardcoding `"compleo"` — correct even if the binary were ever invoked under a different name, and safe in tests too: both calls happen in the same process, so they always agree on what `os.Executable()` resolves to, compiled binary or `go test` binary alike. If the substring isn't found (e.g. a future carapace version changes its own template), `WrappedCompletion` errors instead of silently emitting a snippet whose Tab-press callback still dispatches into compleo.
  - **Gotcha this surfaced, now fixed:** in `complete` mode, `_carapace`'s own completion output is carapace's internal wire format, not zsh — but the wrapped script's `eval "$(compleo parse ...)"` line is unconditional, so it would try to *execute* that wire format as zsh code (confirmed empirically: a real parse error) instead of just passing it through to the generated completion function's own `lines="$(... | xargs greet ...)"` capture. Fixed the same way `EmitHelp`/`EmitError` already solve an analogous problem: `zsh.EmitComplete(wireFormat)` wraps it as `print -r -- <Quote(wireFormat)>\nexit 0`, so `eval`ing it reproduces the wire format verbatim on `greet`'s own stdout (which is exactly what the outer `_greet_completion` function is capturing), then exits before the rest of the script can run.
  - `args[0]` in `complete` mode needs no adjustment: it's already the typed command name (e.g. `greet`), because the xargs-piped compline is the script's own `"$@"` verbatim, and that's exactly what carapace's own `_carapace zsh <name> <words...>` convention already expects as its first argument (used only for value-formatting, per `complete()`'s `.value(args[0], args[len(args)-1])` in `carapace/complete.go`) — so `runParse`'s `complete` branch just does `cmd.SetArgs(append([]string{"_carapace", "zsh"}, args...))` unchanged.
  - Verified end-to-end: `COMPLEO_MODE=generate examples/greet` writes a working `_greet`; sourcing it and driving `_greet_completion` with a real `words`/`CURRENT`/`curcontext` (stubbing `_describe`/`_message`) under real `zsh -f` produces the correct `--loud` candidate, confirming the full round trip (Tab press → generated file → re-invoked `greet` → `compleo` in `complete` mode → wire format → back to the generated file's own parsing).

## Open questions (do not decide silently)

- Whether the spec is a separate YAML file or annotations in the script.
- Whether to adopt `replace github.com/spf13/pflag => github.com/carapace-sh/carapace-pflag v1.3.0`. Needed for full flag-syntax support (shorthand-only flags, non-posix single-dash flags, `nargs`-consuming flags) — without it, those flag forms silently fail to register, with no error surfaced. Tradeoff: a dependency on a pflag fork vs. accepting degraded flag-syntax coverage.
- Nothing yet orchestrates running `COMPLEO_MODE=generate` across every wrapped script a user has — today it's a manual, per-script step (same as Click's `_FOO_COMPLETE=zsh_source foo` pattern this mirrors). Whether `activate` (or something else) should ever try to discover and regenerate wrapped scripts' completions in bulk is undecided.

## Things to verify before relying on them

- The exact name and signature of carapace-spec's macro registration function.
- That current carapace-bin still generates `pkg/actions/actions_generated.go` the way v1.0.2 does.
- Whether carapace-spec's YAML decoder tolerates unknown fields — matters if the same enriched spec file (with compleo's `positionals:`/`flagtypes:` extensions) is ever meant to also be consumable directly by plain carapace-bin/carapace-spec, not just compleo.
- Importing `pkg/actions` links every action package; check the resulting binary size.

## Tooling: mise, not make

Use **mise** for tool versions and tasks. Do not add a Makefile.

- Tool versions (Go, golangci-lint, goreleaser, act) are pinned in `mise.toml` under `[tools]`.
- Simple tasks live in `mise.toml` under `[tasks.*]`; longer scripts are file tasks under `mise-tasks/` (e.g. `mise-tasks/ci-local`) with a `#MISE description=...` header — both run with `mise run <task>`.
- Tasks: `build`, `test`, `lint`, `fmt`, `check` (fmt check, vet, lint, test), `install`, `release-check` (`goreleaser check`, no build), `release-dry-run` (local snapshot build, no publish), `ci-local` (runs `ci.yml` locally via `act`, Docker required).
- If a task you need doesn't exist, add it rather than documenting a raw command here.
- `mise.toml`'s `[env]` sets `COMPLEO_COMPLETION_DIR={{config_root}}/.completions` so `mise x -- go run ./cmd/compleo activate` (or any mise-activated shell) writes into the project instead of the real `~/.local/share/compleo/completions` — convenient for manually inspecting `activate`'s output during development. `.completions/` is gitignored.

## Release & CI

- `.goreleaser.yml`: builds `cmd/compleo` for linux/darwin × amd64/arm64. Relies on GoReleaser's implicit default ldflags (see "Versioning" above) rather than declaring its own.
- `.github/workflows/ci.yml`: `check-ubuntu`/`check-macos` (literal `runs-on`, **not** `strategy: matrix` — see gotcha below) run `mise run check`; `release-check` validates `.goreleaser.yml` on every PR.
- `.github/workflows/release.yml`: runs GoReleaser on `v*` tag pushes.
- `.github/dependabot.yml`: weekly `gomod` + `github-actions` update PRs.
- **act gotchas hard-won while setting up `ci-local`** (all handled in `mise-tasks/ci-local`, don't re-break them):
  - act doesn't read Docker contexts; `DOCKER_HOST` must be set explicitly from `docker context inspect --format '{{.Endpoints.docker.Host}}'` (far more robust than guessing per-tool socket paths — Colima/Rancher Desktop/Docker Desktop all differ, and even Colima's own documented path can be stale across versions).
  - **Confirmed act bug**: `runs-on: ${{ matrix.os }}` under a `strategy.matrix` races when multiple matrix entries evaluate the expression concurrently — they can read each other's resolved platform name (traced to `EvaluateYamlNode` mutating a shared YAML node in act's source). This is *why* `ci.yml` uses two literal jobs instead of a matrix over `os`, not just a style choice.
  - `--container-daemon-socket -` is required to disable bind-mounting the Docker socket into job containers — it fails under any VM-based runtime (Colima, Rancher Desktop) since the host socket path isn't valid inside the VM. None of our jobs need Docker-from-within-a-container anyway.
  - `act push` runs *every* workflow with a `push` trigger, ignoring `release.yml`'s `tags: ["v*"]` filter — `ci-local` scopes to `-W .github/workflows/ci.yml` so it doesn't also attempt (and fail) a real `goreleaser release`.

## Conventions

- Format with `gofmt`; run `go vet` and the configured linter before finishing a change.
- Prefer separate top-level `Test...` functions over table-driven tests, even when it means similar-looking functions repeated — this project's explicit preference, not a Go-wide default.
- Use `testify` (`require`/`assert`) in tests rather than hand-rolled `if err != nil { t.Fatalf }` checks. `require` for preconditions the rest of the test depends on; `assert` for independent checks that should all get reported even if one fails.
- The emitted zsh code is the main contract. Cover it with golden-file tests, and execute the output under `zsh -f` in at least some tests.
- Quoting must be rigorous: arguments can contain spaces, quotes, `$`, backticks, and newlines. Never build emitted shell by naive string concatenation; use one tested quoting function.
- Current package split: `internal/spec` (YAML parsing, types, and building the spec's cobra/completion/usage tree — usage can't be its own package without an import cycle, since it needs `spec.Command`), `internal/parse` (binds a parsed command line to a `Result`), `internal/zsh` (emits the script). Each still testable alone.
- Keep code comments short — one line where possible. Explain the non-obvious *why*, not a paragraph of it.
