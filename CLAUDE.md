# compleo

A Go tool for zsh scripts. One spec file is the single source of truth for three things:

1. **Parsing** the script's command line
2. **Usage / help message**
3. **zsh completion**

The script calls compleo near the top; compleo parses `"$@"` and prints zsh code that the script `eval`s to set variables. Completion is generated from the same spec, so the three never drift apart.

## Status

Early design phase. A Go project skeleton exists (`go.mod` at `github.com/nesneros/compleo`, `cmd/compleo/`, `internal/spec`, `internal/zsh`, `internal/completion`, mise tooling) but no parsing/completion logic is implemented yet. Treat anything under "Open questions" as undecided and ask before choosing.

## Design decisions

- **Language:** Go.
- **Target shell:** zsh only. Emit zsh syntax directly; no bash/POSIX compatibility needed. But the design should be open to extension with e.g. bash later.
- **Completion:** built on carapace. The reason is its rich completion actions (hosts, ssh keys, brew formulae, files, ...). Spec fields for completion should stay as close as possible to the carapace-spec format.
- **Macro names:** use the same names as carapace-spec/carapace-bin (e.g. `$files`, `$carapace.tools...`). Do not duplicate the naming knowledge. The macro names are generated by carapace-bin into `pkg/actions/actions_generated.go` (`MacroMap`, `MacroDescriptions`). Import that map and register its entries instead of hand-writing names.
- **Parsing and usage are extensions:** carapace-spec describes completion only (no required flags, defaults, types, or positional names). compleo adds these.
- **Result delivery:** the Go program prints a zsh script; the calling script `eval`s it. Parsed values go into an associative array (preferred over individual variables).
- **Architecture:** resolved — embed carapace-spec/carapace libraries and build the target spec into an in-memory `cobra.Command` at runtime via `carapace-spec`'s `spec.Command.ToCobraE()`. Explicitly NOT carapace's `--codegen`/`Codegen()`: that's an offline one-shot tool that writes static `.go` stub files (with `Run` always a no-op) for hand-finishing carapace-bin's own completers — it assumes a per-command compile step, which doesn't fit compleo (one generic binary, arbitrary spec read fresh every invocation, no compile step per script).
- **Parsing engine:** resolved — cobra/pflag via `ToCobraE()`, not a custom parser. Caveats: this layer only registers real pflag flags for `string`/`[]string`/`bool`/`count` types (defaults, required, mutually-exclusive flags are all enforced for real by cobra) — other flag types must be coerced by compleo from the string value. Positional args get zero parsing/validation from cobra (`Args` is always `cobra.ArbitraryArgs`) — arity, required-ness, naming, and typing of positionals must be implemented by compleo itself (consistent with the "Parsing and usage are extensions" decision above).
- **Spec delivery at runtime:** the target script's spec is read from compleo's stdin, not passed as a file-path argument. This keeps the calling script free to supply the spec as an inline variable, a heredoc, an embedded string, or an external file it cats in itself. Consequence: in this mode compleo's entire argv is the wrapped script's own arguments — there is no room for compleo's own flags there (see next bullet).
- **compleo's own CLI:** compleo also has a small tool-level CLI of its own (`--help`, `--version`, `--validate`) — a separate invocation surface from the stdin pass-through parsing mode above. Specified via `cmd/compleo/spec.yaml`, dogfooding the same carapace-spec format compleo offers to scripts; loaded via `go:embed` at startup (not yet wired up in code).
- **Canonical carapace org & versions:** the project lives at `carapace-sh` (e.g. `carapace-sh/carapace`, `carapace-sh/carapace-spec`); `rsteube/*` repos now just redirect there and aren't separately maintained. Pin tagged releases: `carapace-spec v1.9.0`, `carapace v1.16.x`, `cobra v1.10.2`, `pflag v1.0.10`.

## Open questions (do not decide silently)

- Whether the spec is a separate YAML file or annotations in the script.
- Name of the associative array (fixed vs chosen by the script).
- Layout for multi-valued results (repeated flags, positional lists): zsh associative arrays hold scalars only, so these need separate arrays or another convention.
- Boolean flag convention in the array (present with a value vs absent).
- Behaviour on `--help` and on bad arguments (likely: the emitted script prints usage and exits).
- Whether to adopt `replace github.com/spf13/pflag => github.com/carapace-sh/carapace-pflag v1.3.0`. Needed for full flag-syntax support (shorthand-only flags, non-posix single-dash flags, `nargs`-consuming flags) — without it, those flag forms silently fail to register, with no error surfaced. Tradeoff: a dependency on a pflag fork vs. accepting degraded flag-syntax coverage.

## Things to verify before relying on them

- The exact name and signature of carapace-spec's macro registration function.
- That current carapace-bin still generates `pkg/actions/actions_generated.go` the way v1.0.2 does.
- Whether carapace-spec's YAML decoder tolerates unknown fields (matters if one file serves both compleo and carapace).
- Importing `pkg/actions` links every action package; check the resulting binary size.

## Tooling: mise, not make

Use **mise** for tool versions and tasks. Do not add a Makefile.

- Tool versions (Go, linters) are pinned in `mise.toml` under `[tools]`.
- Tasks live in `mise.toml` under `[tasks.*]` and run with `mise run <task>`.
- Expected tasks: `build`, `test`, `lint`, `fmt`, `check` (fmt check, vet, lint, test), `install`.
- If a task you need doesn't exist, add it to `mise.toml` rather than documenting a raw command here.

## Conventions

- Format with `gofmt`; run `go vet` and the configured linter before finishing a change.
- Table-driven tests for parsing logic.
- The emitted zsh code is the main contract. Cover it with golden-file tests, and execute the output under `zsh -f` in at least some tests.
- Quoting must be rigorous: arguments can contain spaces, quotes, `$`, backticks, and newlines. Never build emitted shell by naive string concatenation; use one tested quoting function.
- Keep the spec parser, the zsh emitter, and the completion integration in separate packages so each can be tested alone.
